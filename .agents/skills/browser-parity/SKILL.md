# Сверка в браузере и исправление вёрстки

Используй этот навык для «сверь в браузере вёрстку», «проверь вёрстку с оригиналом», замечаний к адаптиву/поведению и аналогичных задач. Цель — максимально близкое соответствие **текущему** `source/`, а не прежнему примеру. Инструмент снимает и диагностирует; исправления в `vanilla/` делает агент. Не заявляй pixel-perfect по одному снимку или без реального браузера.

## 1. Безопасный старт

1. Прочитай `git status --short`, `.doc/tools.md`, проверь, что `source/` и `vanilla/` относятся к одной задаче. Запусти `python -m tools.cli analyze --source source --json` и `python -m tools.cli check --site vanilla --json`. Не трогай `source/` и не запускай старый `build.mjs`. Сохраняй пользовательские изменения; не заменяй каталог целиком.
2. Изучи `source/package.json`, lock, Vite-конфиг и используемые плагины до исполнения. Установка и запуск JS — исполнение недоверенного кода. Используй среду с файловой/сетевой изоляцией и без секретов; временная копия и урезанное окружение сами по себе **не песочница**. Если обеспечить безопасность невозможно, не исполняй подозрительный экспорт, сообщи ограничение. Не выполнять deploy, реальные формы, платежи, авторизацию или изменяющие данные запросы.
3. Проверь Python Playwright, Pillow и Chromium (установка и опциональный локальный кэш в `.doc/tools.md`). При отсутствии браузера не выдавай статику за браузерный тест. Недостающие ассеты и LFS-указатели — **WARN, не блокер**: продолжай доступные действия, сообщай пути и ограничение эталона.

## 2. Снять первый прогон

Из корня, после проверки безопасности:

```bash
.venv/bin/python -m tools.cli browser-audit --trust-source
```

Команда обнаруживает npm/pnpm lock и стандартный Vite, ставит зависимости с `--ignore-scripts` в отдельную временную копию, запускает эталон и статический сайт на разных локальных портах и останавливает процессы. Для другого стека или нестандартного `dev` запускай необходимые серверы отдельно **только после оценки риска** и передай оба URL:

```bash
.venv/bin/python -m tools.cli browser-audit --reference-url http://127.0.0.1:8084/ --candidate-url http://127.0.0.1:8081/ --route /
```

На Windows используй `.venv\Scripts\python.exe`. В обоих вариантах это локальные HTTP URL. Тест не запускает публикацию, не исправляет файлы сам и не является ОС-песочницей.

По умолчанию отличие засчитывается, если хотя бы один канал отличается более чем на 12/255, а допустимая доля — 0,1% экрана. Отчёт также содержит долю любых несовпадающих пикселей. Для побайтово строгой диагностики используй `--channel-tolerance 0 --threshold 0`, но учитывай сглаживание, версии шрифта и нестабильность рендера.

Команда проверяет 390×844, 768×1024 и 1440×900; проходит всю высоту страницы отдельными viewport-снимками, сохраняет `reference`, `candidate`, `diff`, `overlay` и `heatmap` для каждого экрана, длинные `full-*`, снимки сразу после сценария `action-*`, компактный `brief.json` и полный `summary.json` в новом `.work/browser-audits/<id>/`. Сначала прочитай `brief.json` и смотри только нужные карты/наложения, затем соответствующие поля `summary.json`; это экономит контекст. Смотри путь в выводе. Отчёт содержит высоту, результат сравнения видимого текста, видимые контролы, scroll-offset, разницу пикселей, предупреждения и покрытие. Полного сопоставления DOM-элементов и вычисленных стилей пока нет. Снимки могут содержать личные данные: не публикуй их без согласия. Сначала исправляй и переснимай крупную геометрию, затем типографику, изображения, цвета и мелочи. Нельзя обрезать несходящиеся страницы или скрывать отличия маской без явного обоснования.

Если разные или недоступные шрифты делают результаты несопоставимыми, сначала установи причину. Если **подтверждено**, что локальные шрифты результата соответствуют используемому семейству/начертаниям исходника, можно явно передать `--font-css vanilla/css/fonts.css`. Это подставляет файлы шрифта только эталону; отчёт записывает пути и SHA-256, а подмена должна быть оговорена пользователю. Не выдавай такой тест за проверку реального CDN. Без подтверждения не подменяй эталон.

## 3. Поведение и все экраны

Первый запуск проверяет только начальное состояние. По отчёту `controls`, JSX и браузеру составь для **текущего** сайта список меню, раскрытий, табов, якорей, модалок, состояний прокрутки, клавиатуры и маршрутов. Не копируй селекторы из другого проекта. Временно сохрани декларативные сценарии в `.work/`:

```json
[
  {
    "name": "menu-open",
    "viewports": [390, 768],
    "reference": [{"type": "click", "selector": "button[aria-label='Открыть меню']"}],
    "candidate": [{"type": "click", "selector": "button[aria-label='Открыть меню']"}]
  }
]
```

Пути селекторов для React и HTML могут различаться. `viewports` необязателен; если указан, доступны ширины 390, 768, 1440. Каждое состояние начинается с чистой страницы. Допустимы `click` по кнопке без отправки формы, summary или локальному якорю, `focus`, `fill` обычных текстовых полей, `check`, `select`, `press` Tab/Escape/Enter/Space (активация только безопасных элементов), `scroll` с целым `y`; опасные действия и произвольный код запрещены. Используй только тестовые данные: сценарии и снимки сохраняются на диск. Даже безопасная по тегу кнопка может выполнять опасный JS: проверяй назначение и не выполняй действия, которые меняют реальные данные. Запусти заново с `--scenario .work/<файл>.json`. Разные маршруты пройди отдельным запуском с `--route /...`. Для других действий проверь вручную в безопасном браузере и явно укажи, что инструмент их не покрывает. Проверь как минимум открытие **и закрытие**, соответствие `aria-expanded`, Tab/focus и работоспособность доступных состояний.

## 4. Исправить и перепроверить

1. Изучи все отличающиеся/`REVIEW` экраны и реальные причины. Учитывай явно запрошенные намеренные отличия и новую функциональность: проверь их по требованию, не откатывай ради совпадения с React. При отсутствующих файлах не выдумывай логотипы, ссылки, формы и backend; фиксируй предупреждение, сохраняй поведение источника.
2. Правь только нужные HTML/CSS/JS в `vanilla/`, сохраняя содержимое, доступность и пользовательские правки. Устраняй причину, а не подменяй снимок или эталон. Проверяй не только скриншот, но и поведение/клавиатуру.
3. Запусти проверки заново после правок: все три размера, все экраны, сценарии, соседние состояния, затронутые маршруты и статический валидатор. Работай итерациями до устранения подтверждённых различий либо реального ограничения; не останавливайся после первого отчёта.
4. Сообщи кратко, какие файлы исправил, сколько состояний и экранов фактически сверено, какие действия и размеры проверены, где отчёт, что осталось непроверено и какие файлы отсутствуют. `INCOMPLETE` означает, что автоматическая проверка ещё не полная приёмка; `REVIEW` требует просмотра. Нет доказательств полного покрытия — не заявляй, что всё проверено.
