# Обзор проекта и документации

Проверено 25 ноября 2026 года по состоянию репозитория. Это диагностика, а не подтверждение готовности конвертера или визуального соответствия.

## Назначение и фактическое состояние

Цель — преобразовать React-экспорт Figma в качественный самостоятельный сайт на HTML и CSS с минимальным необходимым JavaScript: сохранить контент, внешний вид, адаптив, ссылки и работу интерактивных элементов. Инструмент должен работать с новым экспортом, а не с заранее зашитой страницей.

Сейчас в репозитории находятся **разные проекты и ручной пример**, а не готовый общий конвертер:

- `src/main.tsx`, `src/App.tsx`, `src/index.css`, `public/` — React/Vite/Tailwind-исходник страницы «Как купить квартиру» компании «Энергомонтаж». В нём есть мобильное меню, раскрывающиеся карточки, навигация и ссылки на внешний сайт.
- `.figma/make/site.json` содержит title/description и `robots.index=false` от ФБК «Таргет» и не соответствует текущему React-содержимому. Его нельзя использовать как достоверные SEO-данные исходника без проверки.
- `vanilla/` — отдельный статический сайт ФБК «Таргет», включая страницы игроков, CSS, JS, шрифты и картинки. Он **не является конвертацией текущего `src/`**.
- `build.mjs` содержит данные и HTML этого клуба и записывает только `vanilla/index.html`. Он не читает React-исходник и не извлекает из него стили или поведение. `.doc/templates/build.mjs` идентичен ему и тоже не является универсальным шаблоном; `build-old.mjs` — ещё одна старая версия.
- `package.json`: `npm run build` запускает `vite build`, то есть сборку React в `dist/`, а не создание чистой HTML/CSS-версии. Отдельной команды конвертации и набора автоматических тестов в npm-скриптах нет.

### Опасность перезаписи

Генерация копией `build.mjs` в отдельном временном каталоге показала, что её `index.html` отличается от сохранённого `vanilla/index.html` (в том числе разметкой и подключением шрифтов). Поэтому запуск генератора из корня может затереть существующую работу; не следует считать сохранённый HTML воспроизводимым из этого генератора.

### Ассеты и Git LFS

В этом checkout 24 файла в `src/`, 2 в `public/`, 90 в `vanilla/` и 33 в `.doc/screenshots/` являются текстовыми указателями Git LFS, а не содержимым изображений/шрифтов. Git LFS в окружении не установлен. До визуальной проверки необходимо установить Git LFS и получить реальные объекты (`git lfs pull`, при доступном LFS-хранилище); одних успешно выполненных сборки и проверки существования файлов недостаточно. Это наблюдение относится к текущему checkout, а не утверждение о доступности LFS-объектов на сервере.

Кроме того, `src/App.tsx` ссылается на `/images/logo.svg`, которого нет в `public/images/`; компонент `Image` подставляет запасной текст при ошибке загрузки. Следует проверить другие используемые локальные ресурсы и реальные внешние ссылки отдельно. Текущий исходник использует Google Fonts, а абсолютные пути `/images/...` потребуется аккуратно обработать для размещения в подпапке.

## Обзор и достоверность Markdown-документов

[Карта документов](README.md#карта-документов) описывает каждый файл. Важные противоречия:

1. `00-overview.md` и другие инструкции описывают клуб, прежние массивы, шрифты и структуру страницы, а не текущий `App.tsx`. Там же генератор ошибочно подаётся как универсальная основа; файлы `00–07` оставлены как исторические примеры.
2. `report.md` содержит старый Windows-путь, массивы текущей страницы и CSS/изображения клуба. Это смешанный снимок, не надёжный источник для переноса; `--write` анализатора его перезапишет. Анализатор использует эвристики и регулярные выражения, а не полноценный разбор и исполнение React.
3. Инструкции расходятся с реальной `vanilla/`: кроме `index.html`, там есть страницы игроков, `css/fonts.css` и шрифты. Требование «один CSS» — не описание фактической поставки.
4. Документы запрещают `style=`; это не то же самое, что запрет любого встроенного CSS: в сохранённом `vanilla/index.html` есть блок `<style>`. Правила должны быть сформулированы явно и проверяться соответствующим образом.
5. Vue описан как возможный ручной сценарий анализа, но реализации общего конвертера Vue в репозитории нет. SEO, Lighthouse и pixel-parity в документации — цели, не результаты проверок этого состояния.
6. `07-scripts.md` предлагает удалять служебные файлы из проекта. Удалять генератор или результаты работ без понимания происхождения и резервной копии небезопасно; граница очистки — подтверждённая папка поставки, не весь репозиторий.

Специальные `AGENTS.md` и `CLAUDE.md` оставлены в корне, так как их расположение используется инструментами. Остальные Markdown-файлы собраны в `.doc/`.

## Кандидаты на очистку — после проверки

- 31 файл с суффиксом `Zone.Identifier` — сохранённые Windows-метаданные, а не исходный код. Их можно удалить из Git и добавить правило игнорирования после согласования очистки.
- `.doc/scripts/__pycache__/` — два отслеживаемых Python bytecode-файла; генерируемые артефакты, их можно удалить и игнорировать.
- Два lock-файла (`package-lock.json` и `pnpm-lock.yaml`): определить основной пакетный менеджер перед удалением любого. `.mise.toml` и `.figma/make/install` указывают на pnpm; `npm ci` при этом успешно работает с npm-lock.
- Старые `vanilla/`, изображения клуба в `src/imports/`, `.doc/screenshots/` и шаблоны — наследие другого примера. Не удалять автоматически: сначала решить, нужны ли они как эталон, и проверить ссылки/историю. Снимки и бинарные файлы могут требовать Git LFS.
- `dist/` и `node_modules/` — локальные результаты сборки/установки, уже игнорируются Git.

На этапе обзора содержимое сайта и исторические материалы намеренно не удалялись.

## Рекомендуемый порядок исправления

1. **Зафиксировать область**: текущий React — тестовый вход; определить формат входа/выхода, поддерживаемые React/Tailwind-паттерны, поведение интерактива и критерии готовности. Не обещать произвольный JSX или Vue без реализации.
2. **Восстановить проверяемый эталон**: получить LFS-ассеты, исправить/получить отсутствующие ресурсы, согласовать метаданные, запустить React и снять эталонные снимки на мобильной и десктопной ширинах. Проверить все состояния меню и карточек.
3. **Разделить примеры и инструмент**: архивировать или удалить старый клубный пример по решению владельца; исключить перезапись существующих результатов и сделать явную команду с входной и выходной папками.
4. **Реализовать конвертацию итеративно**: извлечение содержимого и ресурсов, формирование семантического HTML, перенос Tailwind/CSS и адаптива, минимальный JS для состояния и событий. Для неподдерживаемых конструкций выводить понятный отчёт, а не выдавать чужой шаблон за результат.
5. **Добавить воспроизводимые тесты**: фикстуры минимум для двух разных экспортов; проверки контента, ссылок, отсутствующих ресурсов, относительных путей и отсутствия React в результате. Playwright-тесты — для реальных сценариев, адаптива, скриншотного сравнения с исходником и отсутствия горизонтального переполнения.
6. **Очистить и обновить документацию**: после определения границ удалить подтверждённые артефакты, выбрать lock-файл, заменить исторические инструкции на фактические команды и ограничения. Проверять доступность, SEO и производительность инструментами, не подменяя их предположениями.
