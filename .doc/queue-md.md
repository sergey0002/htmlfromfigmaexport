# Агентная Markdown-очередь: формат и переход

Новая очередь предназначена для решений агента, не для автоматического выдумывания страниц. `discover` даёт синтаксические факты. Единственный источник решений в новом режиме — `source/.work/PAGE-QUEUE.md`; служебные marker, HEAD, архив миграции и `queue-history/` — не вторая редактируемая очередь. У текущего проекта пока действует v1: manifest — канон, Markdown — его представление. Не редактируйте текущий v1 Markdown как новый формат до явного cutover.

## Новая очередь

```bash
python -m tools.cli queue-md template --source source --output source/.work/proposal.md --json
# Исследуйте источник и отредактируйте proposal.md
python -m tools.cli queue-md validate --source source --file source/.work/proposal.md --json
python -m tools.cli queue-md commit --source source --file source/.work/proposal.md --expect-absent --reason 'первичное исследование' --json
```

Шаблон не создаёт страниц и не перезаписывает файлы; он не может занимать путь канона, manifest, marker или HEAD. Успешная запись предложения сообщает `operation=applied` (это не commit); при возможной частичной записи или создании каталога — `unknown`. Если уже есть v1 manifest или Markdown без marker, создание канона отказывается; используйте миграцию. После фиксации копируйте канон в новое предложение и фиксируйте с `--expected-sha256 <hash-байтов-канона>` вместо `--expect-absent`. SHA-256 возвращает `queue-md validate --file source/.work/PAGE-QUEUE.md`. Причина обязательна; CLI сохраняет до и после и unified diff в `queue-history/`. При CAS-конфликте перечитайте очередь и вручную объедините изменения. Не используйте один файл одновременно как предложение и канон. Файлы предложений/сценариев должны находиться в `.work/`, без symlink или hardlink; пути и результаты могут содержать личную информацию.

Прямое редактирование канона обходит протокол: несовпадение с HEAD блокирует следующую фиксацию и требует ручного разбора. Lock координирует только текущие совместимые инструменты, не защищает от старых процессов, сторонних редакторов или владельца каталога. При `operation=unknown` не повторяйте запись вслепую; сохраните канон, marker, HEAD и историю для диагностики. История и резервные копии в `.work/` не являются независимым внешним backup.

## Грамматика v1

UTF-8, не более 2 МБ и 10 000 строк таблиц. Ровно одна пара строк `<!-- QUEUE:BEGIN v1 -->` и `<!-- QUEUE:END -->`; текст вне неё — заметки, не исполняется и не является требованиями. Между маркерами строго по порядку таблицы `## meta`, `## pages`, `## aliases`, `## states`, `## resources`, `## issues`. Их заголовки, порядок колонок и разделитель из `---` показаны создаваемым шаблоном. Даже пустые таблицы обязательны. Каждая ячейка однострочная, пробелы по краям обрезаются; для литералов используйте `\|` и `\\`. Другие backslash-escape, управляющие символы, HTML (`<`, `>`) и backticks не допускаются. Остальная разметка не интерпретируется. Неизвестные колонки, секции и версии отвергаются.

- `meta`: фиксированные ключи в шаблоне; после них можно добавить одну строку `template_policy` с относительным путём файла в `.work/`. `source_snapshot` — SHA-256 `snapshot --kind source`, `source_policy=source-v2`, `check_policy=standard-v1`, `discovery_status=unconfirmed|confirmed|review_required`. Для confirmed нужны snapshot, основание, страницы, все страницы confirmed и отсутствие открытых `decision_required`. `legacy_review=not_applicable|unclassified|classified`; после миграции — `unclassified`, подтверждение запрещено до ручного разбора архива. Для `classified` нужна `legacy_review_reason`; мигрированную очередь нельзя переключить в `not_applicable`.
- `pages`: `id`, `title`, `reference_route`, `output`, `confirmation`, `required`, `work_status`, `evidence`, `optional_reason`. ID — строчные ASCII буквы/цифры, `_` или `-`; output — безопасный относительный `.html`; `required=true|false`, а для false нужна причина. Прогресс `pending|in_progress|built|blocked` не является проверкой.
- `aliases`: `page_id`, точный `reference_route`, `purpose`, `evidence`. Конфликты маршрутов выявляются после однократного percent-decoding и Unicode NFC с сохранением раздельных path/query/hash; регистр пути сохраняется. Разные query/hash не считаются эквивалентными автоматически.
- `states`: `page_id`, `state_id` (не `initial`), `required`, `viewports`, `scenario`. Размеры — пары вроде `390x844,768x1024`; сценарий — безопасный относительный путь внутри `.work/` либо пусто. Пустой или отсутствующий обязательный сценарий оставляет покрытие неполным. Текущий браузерный движок поддерживает 390×844, 768×1024 и 1440×900, а не все допустимые размеры.
- `resources`: стабильный `id`, `scope=global|page_id`, `location` (относительный путь в delivery или явный HTTP(S) URL), `required`, `status=unknown|available|missing`, `evidence`. Это заявленный статус агента, а не автоматическая проверка. Запись URL не разрешает сетевой доступ.
- `issues`: `id`, `context`, `kind=decision_required|limitation|info`, `status=open|resolved`, `resolution`, `reason`. При resolved решение и основание обязательны; `duplicate:<page_id>` ссылается на существующую страницу. Решение принимает агент.

Валидация не подтверждает правдивость данных. Канонический requirements hash использует SHA-256 domain `htmlfromfigma.requirements.v1` с завершающим NUL и UTF-8 canonical JSON (sorted keys, compact separators, без Unicode-нормализации), сортирует таблицы по стабильным ID/маршрутам и включает SHA-256 сценариев. `work_status` и свободные заметки исключены; остальные значения включаются консервативно. Фиксированный тестовый вектор пустой очереди с source hash из 64 нулей: `66ad11756056cd95e62c40e8db81eb08e9a3a0b83ff7f715d2522e074aff87c3`. HEAD и история связывают конкретные байты очереди и требования. При изменении подтверждённых требований/сценариев сначала зафиксируйте `review_required`, затем исследуйте и подтвердите заново. При изменении исходника также требуется пересмотр и новый source snapshot.

## Явные отличия общих блоков

По умолчанию размеченные header/footer должны совпадать со статическими `template/header.php` и `template/footer.php`. Если проверенное отличие действительно нужно, агент может сохранить, например, `source/.work/template-policy.json` и добавить **после всех обычных строк meta** строку `| template_policy | template-policy.json |` в предложение очереди:

```json
{"version":1,"exceptions":[{"output":"index.html","block":"HEADER","href":"/index.html","add_class":"active","aria_current":"page","reason":"Текущая страница"}]}
```

В версии 1 допустимы только добавление одного CSS-класса и/или `aria-current=page` к одной конкретной ссылке в одном конкретном блоке страницы; `add_class` и `aria_current` могут быть пустой строкой, но не одновременно. `href` — разрешённый локальный абсолютный путь после разрешения относительно страницы. Для каждого исключения нужны обоснование и ровно одна подходящая ссылка.

Версия 2 дополнительно допускает **точную замену одного token** текста или атрибутов элемента в конкретном блоке и конкретной странице. Она не поддерживает добавление/удаление элементов, изменение имён тегов, wildcard или маски:

```json
{"version":2,"exceptions":[],"substitutions":[{"output":"index.html","block":"FOOTER","index":1,"before":["text","Footer"],"after":["text","Local footer"],"reason":"Осмотренное отличие для этой страницы"}]}
```

Позиция `index` отсчитывается с нуля в **разобранной заготовке**, включая открывающие и закрывающие теги. Токены текста нормализуют пробельные символы; атрибуты в token элемента уникальны и отсортированы, локальные `href`/`src` разрешены относительно `index.html` заготовки или пути страницы. После проверки точного `before` изменяется только этот token; затем применяются исключения активной навигации и сравниваются **все** оставшиеся token. Дубликаты индекса, неизвестные поля, несовпадение старого token, иные изменения и неизвестная версия отвергаются. Каждый выбранный вариант отображается в предупреждениях с обоснованием, даже если сравнение не прошло. Для просмотра индексов и значений без изменения сайта:

```bash
python -m tools.cli template-tokens --site source/.work/staging/example --page index.html --block FOOTER --offset 0 --limit 100 --json
```

Команда показывает окно token заготовки и страницы вместе с delivery snapshot; `replaceable` означает лишь допустимый тип для записи v2. Текст и атрибуты могут содержать чувствительные данные. Чтение ограничено snapshot и 8 МиБ на файл, но не является защитой от гонок родительских каталогов. `HTMLParser` не HTML5-валидатор: комментарии и форматирование не сравниваются, семантику, безопасность атрибутов, наличие и корректность отличия обязан проверить агент. Это ограниченная политика статических блоков, не универсальная политика визуальных или поведенческих исключений.

Файл обязателен при наличии строки, читается без ссылок и входит в requirements hash по байтам. Любое изменение файла/строки для подтверждённой очереди требует промежуточной `review_required` ревизии и повторного подтверждения; до этого `readiness` сообщает о несовпадении. Старые очереди без строки и их фиксированный requirements test vector не меняются. Атрибуты не исполняются, PHP-заготовки остаются статическими и HTML не зависит от PHP.

## Миграция v1

```bash
python -m tools.cli queue-md inspect-legacy --source source --json
python -m tools.cli queue-md migrate-dry-run --source source --output source/.work/migration-plan.json --json
```

Dry-run читает оба файла, сравнивает Markdown с точным v1 render, показывает hashes, страницы/алиасы/состояния и неразобранные ссылки и заметки; готовит предложение с `review_required`. Создание файла плана возвращает `operation=applied` (это не миграция); при возможной частичной записи — `unknown`, файл следует проверить до повтора. Если Markdown вручную изменён, инструмент откажется: разберите обе версии, не перезаписывайте их. Все страницы в предложении временно обязательны, размеры состояний взяты из стандартной политики и должны проверяться. Неизвестные поля, полный v1 manifest, evidence и старый Markdown сохраняются побайтово в локальном архиве, а свободные заметки **не классифицируются автоматически**. Старые проверки не становятся v2 evidence.

Только после успешного dry-run на копии, просмотра предложения и diff, явного решения применить и остановки старых процессов/внешних редакторов:

```bash
python -m tools.cli queue-md migrate-apply --source source --plan source/.work/migration-plan.json --expected-manifest-sha256 <manifest-hash> --expected-markdown-sha256 <markdown-hash> --acknowledge-offline-writers --json
```

POSIX `flock` обязателен; Windows cutover пока заблокирован и не проверялся. Флаг — подтверждение оператора, а не доказательство остановки стороннего процесса. CAS проверяет оба файла и source, создаёт проверенные неперезаписываемые копии и journal до marker/замены. Совместимые v1 readers/writers не используют manifest после marker. Старый код и внешние редакторы могут игнорировать протокол. Уже попытка создания архива может при ошибке вернуть `operation=unknown`; незавершённый архив блокирует новый apply даже до marker. Если journal отсутствует или архив неполон/повреждён, inspect/recover не могут его подтвердить: сохраните файлы и разбирайте состояние вручную, не удаляя архив вслепую. Для проверенного journal:

```bash
python -m tools.cli queue-md migration-inspect --source source --id <id> --json
# Только после проверки архива и остановки внешних писателей:
python -m tools.cli queue-md migration-recover --source source --id <id> --acknowledge-offline-writers --json
```

Если после аварийного завершения остался `.queue.lock`, сначала убедитесь, что работающих писателей нет; только тогда можно явно добавить `--clear-stale-lock` к recovery. Эта опция по подтверждению оператора удаляет stale lock и небезопасна при работающем стороннем писателе. Recovery допускает только подтверждённые хешами старое/новое состояние, не перезаписывает неизвестные изменения. Он завершает прерванный cutover вперёд, не является универсальным откатом или внешним backup. При порче/расхождении остановитесь и разбирайте вручную.

## Диагностика, не приёмка

`coverage --source source --site <candidate>` проверяет статику, локальные ресурсы и строит план page/route/viewport/state с `unknown` для невыполненного. Для v2 diagnostic HTML, CSS, SVG и PHP-заготовки читаются с проверкой размера и SHA-256 delivery snapshot и ограничением 8 МиБ на файл; ресурсы перед проверкой LFS-префикса потоково сверяются с полным hash, в памяти удерживается только ограниченный префикс. `static.fingerprint` в этом режиме равен `null`: v2 digest не подменяет исторический v1 fingerprint (delivery snapshot доступен отдельно). Статические находки не доказывают браузерную корректность; большие текстовые файлы требуют отдельного рассмотрения. Это уменьшает риски замены конечного файла/FIFO, но не защищает от гонок в родительских каталогах, не ограничивает общее время чтения и не является песочницей. Legacy `check` продолжает использовать прежний, не привязанный к v2 snapshot путь чтения. В отдельном `resources` показаны ID, область, обязательность, заявленный статус и наблюдение `present|missing|lfs_pointer|external_unverified`; URL в этом списке не выводится. `present` означает только наличие обычного файла, не его пригодность или соответствие эталону. Локальный отсутствующий обязательный файл и LFS-указатель — ошибки; обязательные внешние ресурсы не запрашиваются и блокируют готовность, как и заявленные `unknown|missing` обязательные ресурсы, даже если локальный файл существует. Необязательные пропуски остаются видимыми в списке. `readiness` и `publish-plan` включают эту диагностику; она не является evidence. `browser-audit-md --source source --site <candidate> --reference-url <локальный-изолированный-url>` выполняет доступные состояния на стандартных размерах и сохраняет артефакты; все успешные состояния остаются `review`, не pass. Сценарии могут содержать ограниченные assertions `visible`, `hidden`, `focused`, `text`, `attribute` для каждой стороны; ошибка assertion даёт FAIL, но полнота проверок, происхождение эталона и ручной осмотр не доказаны; два порта не доказывают независимость. Сценарий может явно выполнять `navigate` с локальным route и `history` с `back|forward` и проверять `focused`; переходы делают GET-запросы и потому допустимы только при оценённом риске side effects. Запускайте внешние серверы и браузер только в надлежащей изоляции: Playwright routing, блокировка service worker/WebSocket и loopback не являются ОС-песочницей.

При `browser-audit-md` и `browser-audit-static-md` успешная запись диагностических артефактов возвращает `operation=applied` даже при статусе `FAIL`/`BLOCKED`; это не публикация и не приёмка. Если после начала создания произошёл сбой, данные изменились или обнаружен противоречивый результат, возвращается `operation=unknown`, частичные файлы сохраняются для разбора. Дочерний `FAIL` не скрывается другой блокировкой, неизвестные, лишние и повторные состояния не считаются выполненными. `run-seal` отвергает сводки, итог которых противоречит ошибкам или блокировкам в дочерних запусках/матрице, а также неполную, лишнюю или повторную матрицу, изменённую обязательность, противоречивые execution/outcome и несоответствующий список сценариев. `run-seal` и `run-inspect` дополнительно сопоставляют каждое состояние матрицы с дочерним результатом и каталогом артефактов: лишние/повторные состояния, отсутствующий каталог выполненного состояния, произвольные пути и `pass`, который диагностический audit не создаёт, отвергаются. Для выполненного состояния обязательны файлы снимков reference, candidate, diff, overlay и heatmap с ожидаемыми путями и последовательными номерами; если заявлены action/fullpage, проверяются и их файлы. Используется inventory snapshot каталога: каждый PNG ограничен 64 МиБ и 12 млн пикселей, считывается с проверкой snapshot, проверяются сигнатура, структура chunks/CRC и размеры IHDR относительно записанной сводки и viewport; анимированные PNG не поддерживаются. Пиксели не декодируются: исправный контейнер с повреждёнными сжатыми данными может пройти. Эта проверка не удостоверяет содержимое, визуальное качество или происхождение и не ограничивает суммарную стоимость аудита. Для заблокированного состояния каталог может отсутствовать. `run-inspect` также сопоставляет итог, счётчики, число файлов, версии браузера и времена записи со сводкой; несовпадение не считается current. Проверяются состав версии браузера и порядок времени в сводке, но эти значения не удостоверяются независимо. Старые неподходящие записи могут потребовать повторного диагностического запуска. Эти механические проверки и hashes не аутентифицируют происхождение отчёта или содержимое скриншотов; полностью согласованная фабрикация остаётся возможной, eligibility не выдаётся.

Явный JSON-массив относительных путей в `.work/` используется `materialize --source source --site <staging> --selection <selection.json> --output source/.work/deliveries/<id>`. Выбираются только перечисленные файлы и директории (директория не включает содержимое автоматически), родительские директории добавляются механически. Отчёт показывает исключения и delivery snapshot. Это `unverified`: состав и отсутствие секретов нужно проверить, а при изменении файлов сформировать новый delivery. Успешное создание возвращает `operation=applied` только для создания копии, не публикации. Ошибка после попытки создания оставляет потенциально неполные файлы и `unknown`.

Права по умолчанию приватные. Явный POSIX-вариант `--permission-profile web-readable --acknowledge-world-readable` делает выбранные файлы потенциально доступными другим локальным пользователям; сначала проверьте содержимое. Хеш прав/uid/gid/mtime связывается с записью delivery v2, но это не проверка работающего веб-сервера или право публикации. Ограничения и риски описаны в [tools.md](tools.md).

`publish-plan --source source --delivery-record <record.json> --target vanilla` показывает diff и hashes без изменения цели; `apply_allowed=false`. Старая `publish` и `record-check --status checked` заблокированы. Доказательная цепочка, доверенный runner и journal/apply/recover публикации ещё не завершены: не объявляйте сайт принятым и не заменяйте `vanilla/` в обход блокировки.

Ручное наблюдение можно отдельно записать `manual-attest --source source --site <delivery> --output source/.work/manual-attestations/<id>.json --actor <actor> --scope <scope> --actions <actions> --outcome pass|fail|incomplete --limitations <limitations>`. Это утверждение с привязкой к source, байтовой ревизии очереди, requirements и delivery, а не подтверждение личности или факт автоматической приёмки. Успешное создание записи возвращает `operation=applied`, при возможной частичной записи — `unknown`; такой файл нельзя считать завершённым. `manual-inspect --source source --site <delivery> --file <file> --sha256 <returned-hash>` валидирует ограниченный формат и сообщает `current|stale` по всем этим зависимостям. `readiness` показывает актуальный заявленный `fail` как блокирующий, но не подтверждает личность заявителя; `pass` не превращается в приёмку. Любые результаты остаются непригодны к публикации до завершения доказательной цепочки.

При сбое записи истории обычный commit возвращает `operation=unknown`, даже если канон ещё не менялся. Неполная или несогласованная по hashes запись истории блокирует новый commit и recovery, включая первый commit: сохраните её для ручного разбора, не удаляйте вслепую. Проверка hashes не аутентифицирует историю и не защищает от произвольного внешнего редактора. При прерванном обычном commit, если известны выбранная корректная запись истории и текущее состояние канона, можно явно завершить только её: `queue-md recover-commit --source source --history <history.json> --expected-sha256 <current-hash> --acknowledge-offline-writers` (для отсутствующего канона — `--expect-absent`). Чужие изменения и устаревшие требования не перезаписываются. При оставшемся после аварийного завершения `.queue.lock` обычный commit/recover блокируется; не удаляйте lock, пока не остановлены все писатели и не сохранены данные для ручной диагностики.
