# Синтетические Linux-эксперименты React/Vite и Chromium

Скрипты принимают только собственные тестовые проекты, не пользовательские пути. Они не являются production runner, гарантией безопасности или доказательством provenance. `managed-isolated` и выполнение произвольного Vite-экспорта остаются недоступны; см. `runner-profiles`.

## Управляемый запуск синтетической фикстуры

`python -m tools.cli runner-synthetic --allow-fixture-registry-network --timeout 120 --json` запускает только фиксированный `isolated-vite-network.sh --synthetic-only`. Внешний исходник или произвольную команду передать нельзя. Флаг явно разрешает сеть registry для зависимостей синтетической фикстуры; код пользовательского экспорта не выполняется. На POSIX контроллер ограничивает время (1–180 с) и совокупный захваченный stdout/stderr (512 КиБ), при завершении, timeout, превышении лимита или SIGTERM/SIGHUP/KeyboardInterrupt посылает сигналы отдельной группе процессов. В отчёт попадают только хвост вывода, код, причина и наличие заранее заданных маркеров. При успешном эксперименте `operation=applied`, `status=INCOMPLETE` и exit 2 — временные файлы/сеть были задействованы; при ошибке после старта `operation=unknown`, exit 4, нужно проверить временные остатки. Маркеры, hashes и диагностика не аутентифицированы и не разрешают публикацию.

Process group — **не cgroup**: процессы могут из неё выйти, суммарные ресурсы не ограничены, собственный SIGKILL контроллера и потеря питания не гарантируют очистку. Синтетический скрипт отдельно создаёт PID namespaces и выполняет свою очистку, но это не доказательство безопасности произвольного проекта. Отчёт может содержать локальные пути; перед передачей удалите чувствительные сведения. Для `managed-isolated` или `managed-local` эта команда не открывает gate.

## Отдельные сети и ограниченные точки связи (синтетический эксперимент)

`tools/spikes/isolated-vite-network.sh --synthetic-only` запускает только фиксированную React/Vite-фикстуру с экспериментальным pnpm-shaped деревом; никаких пользовательских путей скрипт не принимает. Для reference, candidate и браузера созданы отдельные network, root и PID namespaces. В сети каждого сайта работает отдельный доверенный relay с собственным root/PID namespace. Файлы Unix sockets двух HTTP relay доступны только в соответствующем relay и браузерном root, а не в корнях сайтов; браузер создаёт два локальных TCP-моста к ним. Для их настройки также требуется `nsenter`. Зависимости фикстуры заранее скачиваются из registry и проверяются по SHA-512, без npm/pnpm и lifecycle-скриптов.

На доступной Linux-машине проверены различие network namespaces, отсутствие прямого соединения между портами сайтов до и после включения мостов, недоступность прямых портов в браузерной сети до старта мостов, связь каждого relay со своим endpoint, принадлежность listener управляемой группе, strictPort, недоступность тестового host loopback, Chromium без `--no-sandbox` и наличие дополнительного renderer seccomp. Relay ограничивает запросы методами GET/HEAD, фиксированным Host и origin-form путём, отвергает тело, Upgrade/CONNECT, некорректное framing и внешние redirect, не передаёт cookie/авторизацию; установлены экспериментальные лимиты соединений, времени и размера ответа. Тесты проверяют запреты и то, что отклонённые запросы не доходят до синтетического upstream. Браузер открыл обе разные страницы. Отказ relay не дал успешный результат; SIGKILL init контроллера завершил проверенные дочерние процессы и удалил временные корни. Это эксперимент на синтетике, а не проверка безопасности произвольного экспорта.

Передача снимков проверена только для этой фикстуры: браузерный управляющий процесс передаёт через выделенный pipe два PNG (viewport 390×844), ограниченных по длине; контроллер параллельно читает stdout и pipe с таймаутом и ограничением, ждёт закрытия и успешного завершения браузера, проверяет CRC PNG, декодирование Pillow, размеры, число кадров и совпадение SHA-256 с заявленными управляющим процессом. Затем он записывает фиксированные `reference.png`, `candidate.png` и manifest во временный корень, проверяет сохранённые хеши и удаляет корень при завершении. `SPIKE_PYTHON` должен указывать на Python с Pillow и PyYAML (по умолчанию `.venv/bin/python`). Unit-тесты проверяют неверное framing/PNG/размеры и ошибку записи; интеграционные тесты — повреждение и неверные длины снимка, несовпадение заявленного хеша и SIGKILL группы браузера после первого кадра, с отказом и очисткой. При одном наблюдении дескрипторы Chromium проверяются через `/proc`; счётчики доступных и недоступных процессов выводятся в `ARTIFACT_FD_OBSERVATION` и не являются доказательством полной изоляции дескрипторов.

Синтетический network-опыт дополнительно устанавливает через `prlimit` наследуемые hard/soft rlimits до входа в namespace: для процессов сайтов/relay — CPU 30 с на процесс, 256 дескрипторов, 32 МиБ на файл, core 0, адресное пространство 64 ГиБ на процесс; для управления браузером и его потомков — CPU 60 с на процесс, 512 дескрипторов, 64 МиБ на файл, core 0, без ограничения адресного пространства. Контроллер независимо проверяет `/proc/<pid>/limits` у Vite listeners, relay и браузерного контроллера. Отдельный короткий C-процесс в корне фикстуры проверяет невозможность поднять hard limit, `EMFILE`, `EFBIG`, `ENOMEM` и убийство при исчерпании CPU; пределы в негативных тестах дополнительно снижены локально. При сборе браузерных артефактов вывод серверов/relay читается параллельно и ограничен 64 КиБ на сервис; тестовый flood приводит к отказу и удалению временных корней. Установка этих ограничений совместима с этой фикстурой Vite/Chromium на проверенной машине; малые лимиты адресного пространства 2 и 16 ГиБ оказались несовместимы с резервированием виртуальной памяти Node/WebAssembly. Требуются `prlimit` и C compiler.

**Важно:** это ограничения отдельных процессов и отдельных файлов, а не лимиты суммарной памяти, CPU, числа процессов, диска или логов всего дерева. 64 ГиБ виртуального адресного пространства не является физическим memory limit. Потомки могут расходовать отдельные лимиты; отдельные временные файлы и логи вне контролируемого этапа не составляют общую квоту. Rlimits не проверяют все процессы и не предотвращают атаки на ядро или создание процессов. В одном проверенном окружении cgroup был смонтирован read-only; в другом mount отображался как rw, но доступная пользователю иерархия принадлежала root и не была делегирована для записи. Поэтому наличие rw mount не доказывает возможность безопасно создавать дочерние cgroups. Изолированной делегированной cgroup с `memory.max`, `pids.max`, CPU и дисковой квотой для этого runner не подтверждено. Поэтому этот эксперимент не является защитой от resource exhaustion и не снимает блокировку исполнения пользовательского кода.

**Важные границы:** Переданные файлы являются временными тестовыми артефактами, не публикуются и не попадают в evidence; manifest явно содержит `authenticated=false`, `isolated_provenance=false`, `publication_eligible=false`. Хеш, заявленный тем же управляющим процессом, не удостоверяет происхождение снимка и не защищает от подмены отправителем; механизм и PNG-декодер не прошли независимого security audit и не пригодны для недоверенного экспорта. HTTP relay — ограниченный синтетический эксперимент, а не проверенный защитный proxy: он не ограничивает допустимые пути или содержимое GET и не подтверждает происхождение ответов. GET/HEAD могут иметь побочные эффекты; фильтрация методов не делает их безопасными. Браузер имеет доступ к обоим мостам, а Host и маршрутизация Playwright не являются идентификацией клиента или ОС-политикой. Ограничения размера/таймаутов не заменяют системный контроль ресурсов. Нет независимого security audit, полного контроля ресурсов/syscalls, безопасной production-передачи артефактов, защиты от уязвимостей ядра/песочницы или проверки Windows. Подготовка архивов выполняется на хосте без ОС-песочницы. Эти результаты **не** открывают `managed-isolated`, запуск пользовательского проекта или публикацию.

## Раздельные корни и PID namespaces

`tools/spikes/isolated-vite-separated.sh --synthetic-only --browser-sandbox` 27 ноября 2026 г. выполнен на Linux x86_64 с фикстурой React 18.3.1/Vite 5.4.21. Зависимости загружены только из npm registry, проверены по SHA-512 lock-файла и распакованы без npm и lifecycle-скриптов. Серверам reference/candidate и браузеру предоставлены разные файловые корни и PID namespaces; сеть у них общая, но отделена от сети хоста. Участники не имеют Linux capabilities и работают с `no_new_privs`. Браузер запущен без `--no-sandbox`, в доступном окружении у renderer наблюдался seccomp filter. Проверены два endpoint и их владельцы, strictPort на занятом порту, недоступность тестового host loopback, видимость процессов/дескрипторов; SIGKILL init синтетического PID namespace завершил его потомков и временные корни были удалены. `RUN_ISOLATION_TESTS=1 .venv/bin/python -m unittest discover -s tests -p test_isolated_spike.py -v` включает эти интеграционные проверки.

Дополнительный запуск `tools/spikes/isolated-vite-separated.sh --synthetic-only --browser-sandbox --pnpm-fixture` использует экспериментальное pnpm-shaped дерево с внутренними ссылками и отдельным hash, подготовленное без scripts. Lock для синтетического проекта сгенерирован официальным pnpm 10.34.3 командой `install --lockfile-only --ignore-scripts` (без установки пакетов); архив pnpm проверен SHA-512 из registry. При повторении самого опыта pnpm не запускается. Выбраны 15 совместимых пакетов. Два Vite endpoint, браузер, конфликт порта и renderer seccomp проверены в той же схеме. Это не проверка настоящей pnpm installation или пользовательского проекта. Для PyYAML можно задать `SPIKE_PYTHON`, по умолчанию используется `.venv/bin/python`.

Повторение требует Linux x86_64 с поддержкой user/mount/net/PID namespaces, `unshare`, `ip`, `mount`, `setpriv`, `/usr/sbin/chroot`, Node, Python 3, C compiler для sandbox-варианта и сеть к npm registry. Нужны совместимые Playwright/Chromium и библиотеки: по умолчанию скрипт ищет Chromium и библиотеки в `.cache/browser-runtime/`, драйвер — в `.venv/`; пути можно задать `PLAYWRIGHT_CHROMIUM_EXECUTABLE`, `PLAYWRIGHT_CHROMIUM_LIB`, `PLAYWRIGHT_DRIVER_PACKAGE`. Временные файлы находятся в `.cache` и удаляются после штатного завершения; после аварии вне проверенного случая их необходимо инспектировать. Тест ничего не публикует.

Этот предыдущий split-root опыт — **не security audit**: участники имеют общую частную сеть и могут взаимодействовать; защита ядра и backend, исчерпывающий контроль ресурсов, syscall и дескрипторов, доставка артефактов, произвольные конфиги/плагины, host-side подготовка и Windows не проверены. Запускать недоверенный экспорт на основании опыта нельзя.

## Предыдущий общий опыт

`tools/spikes/isolated-vite.sh --synthetic-only` ранее исполнял `npm ci --ignore-scripts` для синтетической фикстуры, затем запускал оба сервера и браузер в общем root/PID namespace и сети. Там Chromium использовал `--no-sandbox`; reference, candidate и browser имели общий UID и могли влиять друг на друга. Проверены два endpoint, strictPort, недоступность тестового host loopback и host project по проверенным путям и `CapEff=0`. Этот опыт слабее нового и так же не разрешает работу с пользовательским экспортом.
