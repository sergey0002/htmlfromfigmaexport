# План внедрения многостраничного режима

Статус: **исторический план: основной многостраничный процесс не завершён; описание ранних этапов и §13 устарело**. Фактические команды и ограничения — в [tools.md](tools.md). Задача — помочь агенту последовательно сверстать все подтверждённые страницы React/Figma-экспорта в статический сайт; это не универсальный автоматический конвертер JSX. Большинство интерфейсов ниже — целевой контракт: не считать их выполненными без проверки реализации. См. краткий статус в конце документа.

## 1. Согласованный результат

- `source/` — исходный экспорт, который не перезаписывается; проектные рабочие файлы располагаются **только** в `source/.work/`.
- `source/.work/PAGE-QUEUE.md` — читаемая очередь; машиночитаемый манифест — единственный источник истины. Отчёты, сценарии, staging и снимки также находятся в `source/.work/`.
- `vanilla/` — полный самостоятельный сайт на статических HTML/CSS/JS, без React и обязательного сервера PHP. Каждая подтверждённая страница — отдельный `.html`-файл: `index.html`, `about.html`, `program/economy.html` и т. д.
- На каждой странице собственные header и footer между одинаковыми комментариями. `vanilla/template/header.php` и `vanilla/template/footer.php` — заготовки из проверенной статической разметки для переноса на CMS; статические HTML их не подключают.
- Общие стили, JS, шрифты и изображения — в `vanilla/assets/`; пути работают на всех уровнях вложенности и при размещении сайта в подпапке.
- Отсутствующие в экспорте страницы не выдумываются: обнаруженные ссылки на них сохраняются отдельно как вопросы. Настоящие формы и интеграции без подтверждённого backend не имитируются.
- Генерация вёрстки, проверка визуала, поведения и доступности включают работу агента; CLI не выдаёт частичные проверки за полную приёмку или pixel-perfect.

## 2. Факты и ограничения текущего checkout

1. `tools/core.py` определяет структуру и проверяет HTML/CSS, но не строит очередь; `check_site` и так обходит все найденные HTML, однако не знает, какие страницы обязательны. `files()` и обход в `analyze()` пока не исключают `.work`.
2. `tools/cli.py`, `tools/browser.py` и `tools/audit_runner.py` ограничивают пути отчётов/снимков корневой `.work/`. `audit_runner._copy_ignore` уже исключает вложенные `.work`, но `fingerprint()` сейчас их учитывает.
3. `screen_audit.audit_urls()` добавляет один `route` к обоим origin; для hash-адреса эталона и отдельного HTML результата нужны независимые маршруты. Дополнительная проверка одной пары не является проверкой всего сайта.
4. В `source/src/App.tsx` предварительно найдены девять основных состояний и шесть деталей программы — **15 кандидатов**, не утверждённая полная очередь. `/` и `/#home` имеют одинаковое содержание; нужно явно записать алиас, а не дублировать страницу.
5. На главной есть `go("about/leadership")`, но ветка `AboutPage` игнорирует `detail`: по коду получается та же страница «О партии», а не подтверждённая биография. Отметить ссылку как неразрешённое намерение/вопрос; не добавлять выдуманную страницу до подтверждения. Это статический вывод, живая проверка ещё нужна.
6. В исходнике есть внешние фотографии и шрифты. Они не попадают в список отсутствующих буквальных локальных ресурсов `analyze`; их доступность, права и необходимость локализации надо проверить отдельно.
7. Зависимости Python устанавливались; браузерные тесты не запускались, скачивание Chromium в этой среде не удалось. Экспортный Vite-код не запускался в полноценно изолированной среде.

## 3. Структура рабочих данных и политика Git

Предлагаемый контракт (точные имена ниже используются во всём плане):

```text
source/.work/
  manifest.json                 # авторитетные данные очереди
  PAGE-QUEUE.md                 # генерируемое человекочитаемое представление
  discovery/                    # отчёты инвентаризации
  scenarios/                    # безопасные сценарии для страниц
  staging/<run-id>/             # единый кандидат всего сайта
  audits/<run-id>/<page-id>/    # снимки и результаты
  reports/                      # сводные отчёты
  backups/                      # только локальные резервные копии при необходимости
vanilla/
  index.html
  about.html
  program/economy.html
  assets/{css,js,fonts,images}/
  template/{header.php,footer.php}
```

- Манифест и Markdown-очередь **предлагается версионировать**, чтобы работу можно было продолжить в следующей сессии; большие снимки, staging, временные и резервные копии, приватные данные и отчёты по умолчанию игнорировать. Не включать в Git реальные формы и персональные данные. Если пользователь предпочитает локальную очередь, изменить политику до внедрения.
- Уточнение к предыдущему сообщению: действующее правило `.work/` в корневом `.gitignore` **уже игнорирует и `source/.work/`**, что проверено `git check-ignore`. Для отслеживаемых очереди и манифеста нужно изменить правила или явно исключить эти файлы из игнорирования; не предполагать, что они сохранятся в Git автоматически. Игнорирование и исключение из сканирования — разные механизмы.
- Предложение для внедрения: заменить общее правило `.work/` на явное `/.work/`, затем добавить `/source/.work/*` и исключения `!/source/.work/manifest.json`, `!/source/.work/PAGE-QUEUE.md`. Проверить `git check-ignore -v` и `git status` на обоих типах файлов; не менять поведение игнорирования иных `.work/` без проверки репозитория.
- При сканировании, поиске манифестов и расчёте fingerprint исключать именно проектную `source/.work/` и другие существующие игнорируемые каталоги; не исключать одноимённые пользовательские файлы вне согласованной области. Факт наличия вложенных symlink и безопасное разрешение путей проверять до копирования/записи. Не сканировать и не запускать рабочие данные как исходник.

## 4. Контракт манифеста и очереди

Версия `schema_version: 1`. Файл UTF-8 JSON; пример **не полная очередь текущего сайта**:

```json
{
  "schema_version": 1,
  "source": {"fingerprint": "<sha256>", "root": "source"},
  "discovery": {"status": "unconfirmed", "unresolved": ["Ссылка на биографию требует проверки"]},
  "pages": [
    {
      "id": "home",
      "title": "Главная",
      "reference_route": "/",
      "reference_aliases": ["/#home"],
      "output": "index.html",
      "evidence": ["src/App.tsx: маршрут home"],
      "confirmation": "candidate",
      "work_status": "pending",
      "states": [{"id": "mobile-menu", "required": true, "scenario": null}],
      "checks": {"static": "not_run", "browser": "not_run", "manual": "not_run"},
      "issues": []
    }
  ],
  "unresolved_links": [{"reference_route": "/#about/leadership", "reason": "Деталь не обработана в AboutPage"}]
}
```

- `id` — стабильный уникальный slug; `reference_route` — локальный путь с возможным hash; `output` — относительный `.html`-путь без query/fragment; один output не может принадлежать двум разным страницам. Дубликаты путей с учётом регистра файловой системы, `..`, абсолютные пути, закодированные обходы, symlink и управляющие символы отклоняются. Алиасы явно привязываются к странице, а не считаются страницами.
- `confirmation`: `candidate` или `confirmed`. Подозрительные и отсутствующие страницы — в `unresolved_links`, а не в обязательном количестве; отключение/удаление ранее подтверждённой страницы допускается только явным решением с причиной. Для проверки полноты список считается подтверждённым только после ручного подтверждения инвентаризации; автоматическое обнаружение не доказывает полноту произвольного React-приложения.
- `work_status`: `pending`, `in_progress`, `built`, `blocked`. Отдельные `checks`: `not_run`, `incomplete`, `fail`, `blocked`, `review`, `checked`; `checked` означает успешное выполнение **конкретной** проверки, не общую приёмку. Итоговое состояние вычислять из полей и доказательств, не вводить противоречащий вручную общий статус.
- Для каждого результата проверки хранить ссылку на отчёт внутри `source/.work/`, отпечаток соответствующего исходника и кандидата, время и область проверки. При изменении входа, страницы, общих CSS/JS/header/footer или сценария затронутые проверки помечаются устаревшими. Изменение общего файла по умолчанию инвалидирует результаты всех зависящих страниц; неизвестную зависимость считать затрагивающей весь сайт.
- Markdown формируется из манифеста детерминированно, без самостоятельного редактирования статусов. Ручные решения вводятся отдельной командой или проверяемым редактированием JSON с последующим обновлением представления. Прерывание не должно уничтожать предыдущий манифест: атомарная запись в той же директории, проверка схемы до замены и защита от параллельной записи/конфликтов.
- При повторном скане сохранять подтверждения, статусы и ручные решения по стабильным ID; изменения показывать как diff и не удалять страницы автоматически. Изменение fingerprint помечает результаты как устаревшие; возможные несовпадения ID и удалённые/новые маршруты требуют подтверждения.
- У каждого рабочего проекта — собственная область `.work` внутри выбранного `--source`, а не только буквальный `source/.work/`. Если корень экспорта обнаружен во вложенном каталоге, рабочая область остаётся под исходным указанным `--source`; команды получают её явно и не выбирают другую неявно. Манифест должен содержать относительную привязку к источнику и параметр версии алгоритма fingerprint, а не зависимый от машины абсолютный путь. Несовпадение источника не разрешается простым изменением ID.
- Подтверждение полноты — отдельное действие с основанием и перечнем оставшихся неопределённостей; нельзя подтвердить пустой список, незавершённый скан или кандидатов без решения по ним. Решение пользователя об отложенном вопросе не превращает непроверенный маршрут в проверенный. Подтверждение оператором означает принятый план работ, а не доказательство автоматической полноты.
- Для аудита хранить полный fingerprint проверенного сайта, а для инвалидации по странице — fingerprint самой страницы и доказуемо связанных общих ресурсов/сценария. Если зависимости определить нельзя, консервативно инвалидировать все страницы. В отчётах не заменять отпечаток проверенного набора файлов новым значением. Если Markdown и JSON разошлись после прерывания, JSON остаётся источником истины и Markdown пересоздаётся с предупреждением, без потери подтверждений и результатов.

## 5. Контракт CLI и статического анализа

Названия ниже — предлагаемый интерфейс, а не действующие команды:

```text
python -m tools.cli discover --source source --work-dir source/.work
python -m tools.cli queue --manifest source/.work/manifest.json --json
python -m tools.cli queue-update --manifest source/.work/manifest.json --page about --work-status in_progress
python -m tools.cli queue-update --manifest source/.work/manifest.json --page about --confirm-page
python -m tools.cli queue-update --manifest source/.work/manifest.json --confirm-discovery
python -m tools.cli check --site source/.work/staging/<id> --manifest source/.work/manifest.json
python -m tools.cli browser-audit --reference-url http://127.0.0.1:8084 --candidate-url http://127.0.0.1:8081 --reference-route '/#about' --candidate-route '/about.html' --work-dir source/.work
python -m tools.cli browser-audit-site --manifest source/.work/manifest.json --source source --site source/.work/staging/<id> --work-dir source/.work
```

`<id>` здесь обозначает существующий ID запуска; это не буквальная команда для копирования. Сначала зафиксировать и протестировать API, затем документировать реально внедрённые флаги.

### Discovery

1. Выполнять статический поиск без исполнения кода: точки входа, маршрутизаторы, `<a href>`, обработчики навигации, literal/вычисляемые пути, источники параметров, контент и состояния. Сохранять путь и место обнаружения, тип доказательства и неопределённости.
2. Не полагаться на один regex как на полноценный парсер TSX; использовать ограниченный поддерживаемый разбор или подключить проверенный AST-парсер как зависимость инструмента. Не устанавливать и не выполнять зависимости экспортного проекта ради статического анализа. При неподдерживаемой конструкции отдавать `unresolved`, а не молча пропускать.
3. По желанию дополнять живым обследованием в **отдельной безопасной среде**; простое нажатие на кнопку может иметь побочный эффект, поэтому не обходить произвольные интерактивные элементы автоматически. Безопасность и доступность проверки не равны доказательству отсутствия скрытых маршрутов.
4. Анализировать ссылки и реализации отдельно: «ссылка есть» не доказывает, что её страница существует. Сопоставлять маршруты с реальными ветками компонентов и доступным контентом; алиасы и fallback фиксировать явно.

### Проверка результатов

- `check --manifest` проверяет все подтверждённые HTML по манифесту, отсутствие дубликатов и конфликтов, счётчики созданных/отсутствующих страниц, внутренние HTML-ссылки и якоря по всем файлам, относительные пути и предупреждения по ресурсам. Отсутствующая обязательная страница — `INCOMPLETE` (или `FAIL` при явно выбранном строгом режиме), никогда не успех. В отличие от существующего `check`, битые внутренние ссылки на HTML/якоря в режиме манифеста должны быть отдельными диагностируемыми ошибками, а не теряться среди предупреждений о ресурсах; ссылки на подтверждённую отсутствующую страницу также учитываются в покрытии. Ссылки-заглушки и внешние ссылки отмечать отдельно, не считать их проверенными реальными адресами. Отсутствующие ресурсы по существующей политике остаются warnings; это не разрешение объявлять страницу визуально проверенной.
- Добавить отдельную проверку шаблонных маркеров и отсутствия PHP-включений в HTML. Искать реальные HTML-комментарии парсером, не обычным совпадением текста внутри `script`/`style`. В каждом HTML ровно одна корректно вложенная пара `HEADER:START/END` и `FOOTER:START/END`, порядок и отсутствие пересечений обязательны.
- `header.php`/`footer.php` — безопасные заготовки статической разметки без исполняемого PHP, полученные из **явно выбранной эталонной страницы**; при использовании относительно разных путей активного меню побайтное равенство не требуется. Зафиксировать нормализованную структурную модель и допустимые различия (`href` относительно расположения страницы и `aria-current`/активный класс); не нормализовать произвольное содержимое. Различия вне списка выдавать как диагностику, не переписывать автоматически. При отсутствии выбранной эталонной страницы сообщить `INCOMPLETE`.
- Отчёты: `schema_version`, fingerprint, список результатов по ID, число подтверждённых/созданных/проверенных, отдельные issues/warnings/unresolved. Статусы CLI и коды остаются совместимы: `FAIL=1`, `INCOMPLETE=2`, `BLOCKED=3`; существующие частичные команды не начинают возвращать общий `PASS`. Для пакетного прогона фиксировать все результаты и применять приоритет `BLOCKED` > `FAIL` > `INCOMPLETE`: невозможность проверки хотя бы одной обязательной области не должна маскироваться обнаруженными ошибками. Предупреждения и `REVIEW` остаются видимыми отдельно; один общий код не заменяет поэлементный отчёт.
- Для отдельных сценариев и ручных проверок предусмотреть обязательность, список viewport, фактические размеры/состояния и ссылку на свидетельство. Наличие файла, статус `built` и неизменный fingerprint сами по себе не означают визуальную или поведенческую проверку. Закрытие каждого состояния и ручные замечания необходимо фиксировать явно.

### Совместимость и пути

- Вынести общий валидатор work-dir для `cli.py`, `browser.py`, `audit_runner.py`: основной `<source>/.work/`; старые явные пути корневой `.work/` поддерживать только в режиме совместимости при явном запросе, с предупреждением и документацией, а не как место хранения новых проектных данных по умолчанию. Не расширять запись на произвольную файловую систему. Уникальные результаты создавать без перезаписи, отклонять symlink/выход за границы work-dir и существующие непустые каталоги; отдельно разрешать атомарное обновление только манифеста и его производной очереди с защитой от конфликтов.
- Зафиксировать обратную совместимость отдельно для изменения defaults и JSON: при запуске старой команды без новых флагов сохранить её семантику результата, объявить изменение каталога артефактов и добавить тесты; поля/коды существующего JSON не удалять и не переименовывать. Новые несовместимые схемы должны иметь другую версию и явную миграцию, а не молча принимать старые записи.
- Старые `analyze`, `check`, `compare`, `browser-audit --route` и JSON-схему не ломать молча. Для старого `--route` сохранить прежнюю семантику; новые парные флаги взаимоисключать с ним. Одностраничный проект остаётся допустимым случаем с одной записью.
- Не перезаписывать `source/` вне разрешённой `source/.work/`; не восстанавливать удалённый legacy `build.mjs`. Ручные/пользовательские файлы сохранять.

## 6. Браузерная сверка и безопасность

1. В `screen_audit.py` принимать `reference_route` и `candidate_route`, валидировать как локальные относительные маршруты; сохранять query/hash и URL-энкодинг корректно. Сформированные URL должны оставаться на разрешённом origin; запрет `//`, внешних схем, обходов и переходов за origin не ослаблять.
2. `browser-audit-site` читает подтверждённый манифест, для каждого page ID выполняет проверку на 390×844, 768×1024, 1440×900 и всех применимых состояниях. Для каждой пары — отдельный каталог; выдать агрегат и ошибки по каждой странице, продолжить безопасные независимые проверки после ошибки страницы.
3. Для разных DOM использовать разные действия сценария эталона и результата, как уже предусмотрено `load_scenarios`. Добавить безопасную проверку прямого адреса и навигации между страницами, обновления, back/forward и вложенных относительных ссылок. Не разрешать произвольный код или отправку форм под видом сценария.
4. В отчёте отделять `planned`, `checked`, `skipped`, `blocked`, а также `FAIL`/`REVIEW` по странице и viewport. Отсутствие Chromium, эталона, обязательного состояния, файла или недоступный ресурс не скрывать успешной общей статистикой. Визуальные результаты не заменяют ручную проверку клавиатуры, доступности и семантики.
5. При автоматическом запуске экспортного Vite использовать полноценную изоляцию ОС/контейнер без секретов и с ограничениями filesystem/network, отдельную копию и ограниченные права. `--trust-source`, `--ignore-scripts`, временная папка и блокировка запросов Playwright сами по себе **не песочница**; при недоступности изоляции выполнение источника остаётся `BLOCKED`. Отдельно обеспечить доступ preview через разрешённый прокси, не открывая доступ к секретам/внутренним сервисам. Без этого делать только статический анализ.
6. Снимки и сценарии могут содержать личные данные. Только тестовые данные, без реальных отправок; их нельзя публиковать без согласия. Внешние CDN-ресурсы перечислять в предупреждениях, доступ к ним не открывать неявно.
7. Проверки с заранее запущенными `--reference-url`/`--candidate-url` тоже выполняют JS и обращаются к loopback-сервисам: запускать их только в изолированном окружении без чувствительных сервисов, а не считать безопасными из-за фильтра origin. GET может менять данные. Не раздавать `source/.work/` по HTTP: для превью выдавать только отдельный корень кандидата, без симлинков и доступа к соседним путям; артефакты и резервные копии остаются закрытыми. Режим запуска и реальную изоляцию записывать в отчёт, но `--trust-source` не считать доказательством изоляции.

## 8. Поставка и возобновление

- В начале записывать fingerprint исходника без `source/.work/` и состояние `vanilla/`. Строить весь сайт в уникальном `source/.work/staging/<run-id>/`, не смешивать старый и новый экспорт.
- Пока страницы не готовы, очередь отражает незавершённость; возобновление по ID не перезаписывает другие страницы и не пропускает устаревшие проверки общих ресурсов.
- До переноса получить данные о существующей `vanilla/`, сделать и проверить резервную копию; при риске потери пользовательских изменений запросить разрешение. Проверить достаточность места, права и целостность резервной копии, затем подготовить полную копию результата рядом с целевым каталогом. Не обещать атомарную замену непустой директории на всех ОС: явно предусмотреть журнал шагов, неудачу копирования/переименования, прерывание и восстановление. Не удалять резервную копию автоматически и не считать игнорируемую Git локальную копию долговременным внешним бэкапом. Никакого деплоя и очистки без разрешения.
- После переноса проверить именно итоговую `vanilla/`, её fingerprint и все обязательные файлы. Отчёт показывает, что проверено, а что заблокировано или остаётся на ручную проверку. Отсутствие браузера не мешает доступной работе, но не позволяет назвать визуальную приёмку выполненной.

## 9. Этапы внедрения и критерии готовности

### Этап A — инвентаризация этого экспорта

**Результат:** подтверждаемая очередь, список отсутствующих/неясных направлений, список ресурсов и состояний. Сначала доступный статический анализ, затем безопасная живая проверка при наличии изоляции. Проверить как минимум 15 кандидатов и отдельно `about/leadership`; не обещать полный список до подтверждения. Этот этап не создаёт сайт и не требует завершённого CLI.

### Этап B — рабочая область и манифест

Изменить игнорирование и обходы, реализовать схему/валидацию, атомарную запись, генерацию Markdown и инвалидацию статусов. Тесты на fingerprint без рабочих файлов, пути/симлинки, повторный скан и сохранение решений, git-ignore, прерывание и одновременные изменения. **Готово**, когда очередь воспроизводима и не загрязняет исходный анализ.

### Этап C — discovery и coverage

Реализовать ограниченное статическое обнаружение и отчёт неопределённостей, `check --manifest`, счётчики, диагностику маркеров и ссылок. **Готово**, когда пропущенная обязательная страница выявляется, а сомнительный маршрут не превращается в выдуманную страницу; старый `check` без манифеста продолжает работать.

### Этап D — браузерные пары и пакетный аудит

Независимые маршруты, пакетные сценарии, изолированные каталоги снимков и агрегат без скрытых ошибок; поддержка старого `--route`. **Готово**, когда тестовая пара `/#program/economy` → `/program/economy.html` и сайт с несколькими состояниями корректно проверяются, а отсутствие браузера даёт явный `BLOCKED`.

### Этап E — навыки и безопасный процесс

Обновить три навыка, корневые инструкции и документацию; определить контракт шаблонов и публикации, снабдить примерами одностраничного и многостраничного проектов. **Готово**, когда новый агент может продолжить работу по очереди без противоречащих инструкций и не выдаёт неполную проверку за приёмку.

### Этап F — пилот на текущем проекте

После внедрения A–E и отдельного поручения на вёрстку: создать staging, сверстать весь подтверждённый список, проверить и только затем рассмотреть перенос в `vanilla/`. **Готово**, когда покрытие каждой подтверждённой страницы и каждого обязательного состояния прозрачно, все статические ссылки и ресурсы проверены, а непроведённые браузерные/ручные проверки явно перечислены. Если браузер недоступен, пилот остаётся неполным.

## 10. Обязательная матрица тестов

- **Unit:** схема и ошибки JSON, пути (`..`, абсолютные, query, fragment, symlink, Unicode/регистровые коллизии), алиасы, дубли output, пустая очередь, невозможные/неподтверждённые маршруты, кодировки, стабильные ID, атомарность и неизменность исходника, fingerprint без `.work`, сохранение статусов и инвалидация.
- **Discovery:** синтетический hash-SPA с кнопками и конечным массивом динамических параметров, обычная MPA, статическая одна страница, недоступные вычисляемые пути; ссылка с fallback отдельно от существующей страницы. Никаких утверждений об универсальной полноте на основании одного примера.
- **Статика:** отсутствующая обязательная HTML-страница, ссылки между вложенными страницами и битые якоря, пути относительно подпапки, незакрытый/повторный/пересекающийся маркер, текст маркера внутри script, разные активные меню, блоки вне допустимых различий и отсутствие PHP include в HTML.
- **Browser integration:** отдельные URL двух сторон, hash, query, вложенные пути и base path; все viewport/состояния, прямое открытие, back/forward; различия на нижних экранах; отсутствующие изображения/шрифты; отказ внешнего origin, отказ на опасных действиях; ошибка одного маршрута не скрывается агрегатом; прерывание, отсутствие браузера и безопасное завершение процессов. Использовать Chromium и синтетические страницы.
- **Регрессия:** существующие unit и браузерные тесты, старый CLI и `--route`, сайты без манифеста и один маршрут. Выполнять `python -m unittest discover -s tests -v`, затем `RUN_BROWSER_TESTS=1` при установленном Chromium; пропуски явно отражать.
- **End-to-end:** новый проект → обнаружение и подтверждение очереди → staging и частичное возобновление → повторная проверка после изменения общего CSS → неразрушающий перенос → проверка `vanilla/`. Отдельно тестировать существующую `vanilla/`, отказ в разрешении на замену, прерывание и восстановление копии.

## 12. Результат финального аудита плана

План повторно сопоставлен с `tools/core.py`, `tools/cli.py`, `tools/audit_runner.py`, навыками, `.gitignore` и навигацией `source/src/App.tsx`. Код движка и сайт в рамках аудита не менялись; браузер и новый функционал не тестировались.

В ходе аудита уточнены пункты, которые могли привести к ошибочному внедрению:

- Рабочая директория должна корректно привязываться к произвольному `--source`, в том числе при вложенном корне проекта; игнорирование Git не заменяет исключение из fingerprint.
- Подтверждение очереди, восстановление Markdown из JSON и инвалидация результатов должны быть явными; отпечаток всего сайта нельзя незаметно подменять отпечатком одной страницы.
- Отсутствующие страницы и битые ссылки нужно учитывать отдельно от предупреждений о ресурсах; при пакетной проверке одна ошибка или блокировка не должна теряться в общей статистике.
- Совместимость прежних путей не должна превращать корневую `.work/` в новое место хранения по умолчанию. Изменение defaults и версий JSON требует отдельной миграции.
- Проверка готовых URL и предпросмотр тоже требуют изоляции; нельзя отдавать по HTTP всю рабочую папку с отчётами и резервными копиями.
- Перенос сайта не всегда может быть атомарным, а игнорируемая локальная копия не является надёжной долговременной резервной копией.

**Вывод:** план пригоден для начала этапа A и проектирования этапа B, но не является завершённой реализацией. Открытые решения из раздела 11 и технический выбор изолированной среды остаются до начала соответствующих этапов. Полнота очереди и визуальная приёмка текущего сайта пока не подтверждены.
