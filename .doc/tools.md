# Инструменты многостраничной вёрстки

Инструменты в `tools/` помогают агенту вести очередь, фиксировать диагностические результаты и проверять сайт. **Они не являются автоматическим конвертером React в HTML и не гарантируют обнаружение произвольных динамических маршрутов.** Вёрстку, интерпретацию макета, визуальные исправления и ручную проверку выполняет агент.

## Установка

Python 3.10+ (в данном окружении проверен 3.11; tree-sitter 0.25.2 не поддерживает 3.9):

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r tools/requirements.txt
.venv/bin/python -m playwright install chromium
```

Для Linux x86_64 и CPython 3.11 доступен также полный lock с hashes: `python -m pip install --require-hashes -r tools/requirements-lock-linux-py311.txt`. Другие ОС/версии Python требуют собственного lock; Windows не проверялся.

Для статического AST-анализа нужны pinned `tree-sitter`, `tree-sitter-typescript` и `tree-sitter-javascript`; при их отсутствии обнаружение остаётся неполным с предупреждением. Один Chromium достаточен; эталон и результат должны проверяться одной версией. В некоторых средах скачивание Chromium недоступно или нужны системные библиотеки. Если есть совместимый локальный Chromium, задайте `PLAYWRIGHT_CHROMIUM_EXECUTABLE` и при необходимости `LD_LIBRARY_PATH`. На Windows используйте `.venv\Scripts\python.exe`.

## Проектная область и очередь

Все новые проектные файлы — в `<source>/.work/`:

- Для v1 `manifest.json` — очередь, а `PAGE-QUEUE.md` генерируется из неё; после отдельного cutover единственный редактируемый канон — структурированный `PAGE-QUEUE.md` ([формат и миграция](queue-md.md)).
- `staging/<id>/` — полный кандидат сайта; `scenarios/`, `audits/` и `reports/` — рабочие файлы и доказательства.
- `backups/` и `publications/` — локальные копии при разрешённой замене. Они не являются независимым внешним бэкапом.

Для текущего `source/` манифест и очередь разрешены правилами Git, но могут быть ещё не добавлены в индекс; тяжёлые/временные файлы игнорируются. Не сохраняйте в очередь и отчёты персональные данные. Входной экспорт вне `.work/` не перезаписывается. Сканирование и fingerprint исключают рабочую директорию. Переходный legacy `analyze` и v1 fingerprint отказываются работать при наличии `.env*` или вложенной `.work`, не читая их: старую identity нельзя молча изменить. Для безопасного инвентаря без `.env*` используйте `snapshot --kind source` и `discover`; это не устанавливает совместимость с v1.

```bash
.venv/bin/python -m tools.cli analyze --source source --json
.venv/bin/python -m tools.cli discover --source source --json
.venv/bin/python -m tools.cli queue --source source --json
```

`analyze` по умолчанию скрывает значения npm scripts/версий и найденных literal src, возвращая количества; для явного просмотра чувствительных исходных строк есть `analyze --include-source-text`. Имена файлов, пути и хеши тоже могут содержать или раскрывать чувствительные сведения; проверяйте отчёты перед передачей. `analyze` поддерживает статический HTML без npm и один вложенный npm-корень; перечень HTML не означает подтверждённые страницы. При наличии нескольких package.json требуется ручной выбор. Legacy анализ не охватывает исключённые генерируемые каталоги. `discover` сейчас только читает файлы и возвращает синтаксические факты с источником и координатами, а не список страниц; пагинация `--offset 0 --limit 100` (максимум 500). Он не создаёт и не изменяет manifest. По умолчанию текст фрагментов JS/TS и значения HTML-атрибутов скрыты. Опция `--include-source-text` раскрывает потенциально чувствительные данные; проверяйте отчёт перед передачей. `--file` разбирает указанный файл, но snapshot охватывает весь допустимый источник. `queue` показывает существующий v1 manifest и вычисляет `stale` в памяти, но не записывает его или Markdown. Отпечаток файла манифеста возвращается как `manifest_sha256`. Для новых проектов доступны `queue-md template/validate/commit`; переход v1 поддерживает inspect, dry-run и journaled cutover с ограничениями — см. [queue-md.md](queue-md.md). `discover` сам очередь не создаёт. Старый `queue-update` ограничен существующими страницами и ссылками; изменение источника блокирует его. Непроанализированные свободные заметки v1 блокируют новое подтверждение инвентаризации. Не обходите ограничения ручной правкой ради ложной приёмки.

```bash
.venv/bin/python -m tools.cli snapshot --root source --kind source --json
.venv/bin/python -m tools.cli snapshot --root source/.work/staging/example --kind delivery --json
```

Snapshot v2 разделяет политики source (исключает `.work`, `.env*` и генерируемые каталоги) и delivery (все файлы), включает пустые каталоги и отвергает ссылки, hardlinks, специальные файлы и конфликтующие имена. Регистрочувствительная версия v2 не переопределяется молча: вместо чтения или исключения неоднозначные варианты имён вроде `.ENV` и `.WORK` блокируются до чтения/обхода и требуют ручного разбора; legacy fingerprint/analyze также отказываются от вариантов `.env*` и `.work` независимо от регистра. Список исключений возвращается в результате. При `discover` допустимый файл читается с ограничением и сверкой содержимого с предварительным snapshot до разбора; изменение либо ссылка блокируют результат. На поддерживающих POSIX системах nonblocking open снижает риск зависания при подмене файла FIFO. Сам снимок read-only: legacy проверки по-прежнему используют **старый v1 fingerprint**, а новые `materialize`, `coverage`, `browser-audit-md` и ручные аттестации применяют снимки v2; безопасная публикация ещё не реализована. Эти проверки не защищают от всех гонок, включая подмену родительских каталогов, и не заменяют остановку сторонних писателей или ОС-изоляцию; на Windows не проверены. Имена не выявляют все секреты. Не считать снимок доказательством источника.

## Проверка сайта

Поставка — отдельные `.html`-файлы, общие `assets/`, статически продублированные header/footer. В каждом HTML должны быть комментарии `<!-- HEADER:START -->`, `<!-- HEADER:END -->`, `<!-- FOOTER:START -->`, `<!-- FOOTER:END -->`. `template/header.php` и `template/footer.php` — статические заготовки, не подключаемые к HTML. Проверка сопоставляет содержимое блоков с заготовками, нормализуя относительные `href`/`src`, но по умолчанию сравнивая все атрибуты, включая `active` и `aria-current`. В новой очереди `template_policy` v1 допускает обоснованное добавление класса и/или `aria-current=page` конкретной локальной ссылке; v2 дополнительно поддерживает точечные замены конкретных text/attribute token с исходным и новым значениями и обоснованием. Другие отличия не игнорируются; инструкция и `template-tokens` для просмотра индексов описаны в [queue-md.md](queue-md.md). Это не универсальная политика визуальных исключений; автоматическое сравнение блоков не является HTML5-валидатором или проверкой безопасности разрешённых атрибутов.

```bash
.venv/bin/python -m tools.cli check --site source/.work/staging/example --manifest source/.work/manifest.json --report source/.work/reports/static-example.json
```

`check` без манифеста сохраняет одностраничную совместимость. С манифестом он также проверяет наличие подтверждённых страниц, часть локальных ссылок/якорей, маркеры, PHP-заготовки и PHP-ссылки. Консервативная проверка подтверждённых HTML отвергает любое `<?` (в том числе XML processing instruction как возможное ложное срабатывание) и буквальные PHP-пути в URL-атрибутах, включая action/formaction, srcset, percent-encoding одного уровня и path-info; это не полный анализ JS/CSS, серверной маршрутизации или всех способов вызвать backend. Нет всех страниц, браузера, состояний или ручных проверок — нет полной приёмки. Отсутствующие ресурсы и LFS в общей проверке — предупреждения, но обязательные локальные ресурсы очереди учитываются отдельно в `coverage`; см. [queue-md.md](queue-md.md). Ссылки из JS, вычисляемые пути, не все виды CSS и внешние адреса эта проверка не охватывает.

## Браузерный аудит

Никогда не запускайте недоверенный экспорт или его зависимости рядом с секретами. Временная копия, `--ignore-scripts`, ограничение origin и `--trust-source` не являются ОС-песочницей. **Автозапуск Vite в CLI отключён**. Агент может использовать заранее запущенный эталон только в полноценной файловой/сетевой изоляции без секретов и чувствительных сервисов; при её отсутствии продолжайте статическую работу и честно сообщите `BLOCKED`. GET также может менять данные; реальные формы не отправлять.

Для одной пары в изолированной среде:

```bash
.venv/bin/python -m tools.cli browser-audit --source source --reference-url http://127.0.0.1:8084 --candidate-url http://127.0.0.1:8081 --reference-route '/#about' --candidate-route '/about.html'
```

Старый `--route` задаёт один маршрут обеим сторонам и несовместим с парными параметрами. Для всего подтверждённого манифеста:

```bash
.venv/bin/python -m tools.cli browser-audit-site --source source --site source/.work/staging/example --reference-url http://127.0.0.1:8084
```

В пакетном режиме CLI временно раздаёт указанный кандидат на loopback и закрывает сервер. Скрытые файлы/каталоги (включая `.work` и `.env`), symlink, hardlink и специальные файлы внутри кандидата запрещены; directory listing отключён; сервер отдаёт только перечень обычных файлов, сформированный при запуске, добавленные позже файлы недоступны. Это не снимок содержимого: существующие файлы могут изменяться. Имена не выявляют все секреты: агент должен проверить состав отдельного кандидата. Проверки путей не защищают от всех гонок и не заменяют изоляцию. Явный `--candidate-url` также разрешён для диагностики, но привязка такого URL к файлам кандидата не подтверждена. В переходном режиме никакой отчёт не принимается как `checked`. Запросы Playwright вне origin и методы кроме GET/HEAD блокируются; это не заменяет изоляцию ОС.

Аудит проверяет 390×844, 768×1024 и 1440×900, каждый экран по высоте, текст, элементы управления и разницу изображений. Сценарии для двух сторон могут иметь разные селекторы; их формат описан в `.agents/skills/browser-parity/SKILL.md`. Каждая страница может ссылаться на один JSON-файл сценариев в `.work/`; имена обязательных состояний должны совпадать. Пропущенные сценарии выводятся как предупреждения. Отчёты содержат `brief.json`, `summary.json`, `reference`, `candidate`, `diff`, `overlay`, `heatmap`; долгие снимки и состояния могут быть ограничены. Проверяйте также клавиатуру, открытие/закрытие, семантику, навигацию, прямые URL и историю вручную; не выдавайте один снимок за полную проверку.

## Сохранение доказательств и перенос: переходный режим

`record-check --status checked` и `publish` **временно отключены**, включая прямые вызовы Python: v1 не связывает проверки с текущими требованиями и достоверным эталоном. Существующие `checked` при чтении отображаются как `stale`, без перезаписи файла. Остальные статусы record-check предназначены только для фиксации неполной работы; их старые отпечатки не означают проверенный delivery. Не переносите пользовательские файлы и не объявляйте сайт принятым в обход этих ограничений. Миграция очереди и диагностический `publish-plan` доступны. Добавлены экспериментальные журналируемые механизмы `publish-apply`, `publication-inspect`, `publication-restore`, но `publish-apply` всегда блокируется до полной цепочки evidence и проверенных gates; механизм сам по себе не разрешает публикацию.

`--report` до команды резервирует новый JSON-файл непосредственно в `.work/` или `<source>/.work/`, либо внутри их `reports/` (для `check --manifest` также допустима рабочая папка рядом с manifest). Вложенные пути вне `reports/`, скрытые имена, файлы очереди, symlink и пересечения с путями входа/выхода команды отклоняются; существующие файлы не перезаписываются. Это более узкий контракт, чем прежнее разрешение произвольных вложенных путей. Проверки не исключают гонки со сторонними писателями. Ошибка предварительной проверки возвращает `operation=not_applied`, `report_operation=not_applied`; после попытки резервирования при сбое команда ещё не выполнялась, но `report_operation=unknown` и код 4: каталог или файл могли остаться. После успешной записи и синхронизации stdout показывает `report_operation=applied`, а `operation` относится к самой команде; сохранённый JSON не утверждает успешность собственной записи. При ошибке финальной записи stdout возвращает код 4, `operation=unknown`, `report_operation=unknown` и результат команды, если он известен; это не журнал восстановления. При аварийном завершении без ответа нельзя определять состояние лишь по наличию отчёта — проверьте также результат самой команды. При ошибке сохранения `record-check` после попытки изменения очереди возвращается `ERROR=4`, `operation=unknown`: пара v1 manifest/Markdown не является транзакцией; прямой Python-вызов поднимает `MutationUncertainError`. При проблемах сохраняйте обе версии и диагностируйте вручную, не запускайте повторно вслепую.

### Экспериментальный журнал публикации (POSIX)

`publish-plan --delivery-record ... --report source/.work/<новый-файл>.json --json` создаёт диагностический отчёт; `publish-apply --plan ... --sha256 <хеш-байтов-отчёта> --acknowledge-offline-writers` перепроверяет его, но сейчас всегда отказывает. Подделка отчёта не открывает gate. Тесты применяют mock gate исключительно к временным фикстурам; на пользовательских данных apply не запускался.

`publication-inspect --id <id> --json` показывает фазу, hashes цели, локального backup, подготовленной и сохранённой новой копии, а также snapshot/метаданные и пригодность имеющейся `restore-copy`. Любая ошибка после попытки создания каталога, журнала или копии сообщает `operation=unknown`, даже если цель ещё не заменялась. Незавершённый или повреждённый журнал блокирует новый apply; `published_unverified` также не считается завершённой приёмкой и блокирует следующий apply до восстановления. Если журнал отсутствует/повреждён, автоматический inspect/restore может быть недоступен — сохраните данные и разбирайте вручную. `publication-restore --id <id> --expected-target-sha256 <hash> --acknowledge-offline-writers` или `--expect-target-absent` явно восстанавливает старую копию, сохраняя новую; неизвестное дерево или изменённый backup блокируют действие. После копирования backup повторно проверяются цель, журнал и записанные деревья до первого переименования; это не исключает гонку после проверки. Это потенциально изменяющая команда: сначала остановить внешних писателей, проверить журнал, состояние и независимый backup. После аварийного завершения может потребоваться `--clear-stale-lock` только после проверки отсутствия других писателей. При `ERROR/unknown` не повторять вслепую; ещё раз проверить журнал и файлы. При прерванном копировании `restore-copy` может остаться неполным: инструмент откажется его перезаписывать, требуется ручной разбор с сохранением данных.

**Ограниченный POSIX-профиль метаданных:** обычный snapshot v2 по-прежнему учитывает только имена, типы и содержимое. Для экспериментальной публикации отдельно вычисляется hash режима доступа, числовых uid/gid и `mtime` каждого файла и каталога, включая корень. План показывает `delivery_metadata`/`target_metadata`; журнал v2 связывает старые и новые значения, `inspect` проверяет их наряду с содержимым, а restore копирует и перепроверяет этот ограниченный набор. Отвергаются ссылки, специальные биты и видимые xattrs/ACL; ошибка их перечисления также блокирует обработку. Владелец и группа создаваемых объектов должны совпадать с исходными — `chown` не выполняется; неисполняемые/нечитаемые владельцем каталоги и нечитаемые файлы не поддерживаются. Старый журнал v1 доступен для просмотра, но автоматический restore по нему отказывает: в нём нет hash метаданных, требуется ручной разбор с сохранением данных.

Это **не полноценное восстановление метаданных**: atime, ctime, birth time и иные платформенные атрибуты не сохраняются; проверка видимых xattrs не является универсальным аудитом ACL, меток безопасности или файловой системы. По умолчанию `materialize` создаёт приватный delivery; опциональный профиль `web-readable` описан ниже, но доступ веб-сервера не подтверждён. `backup_valid` для журнала v2 означает соответствие только содержимого и поддерживаемого подмножества, а не полноту архива. Исходное дерево `previous` сохраняется, локальный backup не заменяет независимый. `publish-plan`, `publication-inspect` и результат restore сообщают ограничения. Транзакция и restore проверены частично: на временных фикстурах с mock gate проверены сбои до/после rename и journal, ошибки fsync, а также реальный SIGKILL после каждого restore rename и записи двух фаз журнала с последующим явным восстановлением. При `FAIL` или `BLOCKED` статической post-check журнал фиксирует `postcheck_failed`; исключение, неизвестный/противоречивый ответ и несовпадение snapshot оставляют состояние неопределённым и не переходят в `published_unverified`. После первичной диагностики source, очередь, целевое дерево и метаданные проверяются повторно; это не исключает гонки после проверки. После любой такой ошибки обе версии сохраняются для явного восстановления; автоматической браузерной или ручной приёмки нет. Это не проверка реальной потери питания или всех файловых систем; нет полной fault matrix, браузерной/ручной post-publication приёмки, поддержки Windows или гарантии от некооперативных гонок.

## Статусы, совместимость и тесты

Коды: `FAIL=1`, `INCOMPLETE=2`, `BLOCKED=3`, `ERROR=4` (IO/неизвестное состояние после попытки мутации). Частичные автоматические команды не выдают общую приёмку. Старые `analyze`, `check`, `compare` и `browser-audit --route` сохранены; явные прежние пути отчётов внутри корневой `.work/` допускаются для совместимости. Не восстанавливайте legacy `build.mjs`.

```bash
.venv/bin/python -m unittest discover -s tests -v
```

Тесты используют временные синтетические страницы; запуск браузерных тестов требует установленного Chromium. Скриншоты и сценарии могут содержать чувствительные данные — не публикуйте их без согласия.

## Новая очередь и delivery

Команды и точный формат — в [queue-md.md](queue-md.md), включая ограниченную политику явно подтверждённых отличий активной навигации. `materialize` создаёт отдельный непроверенный delivery по явному списку, `coverage` строит статическую матрицу, `browser-audit-md` выполняет диагностический Chromium-аудит с `external-unverified` эталоном, а `publish-plan` только показывает diff. Ни одна из них не открывает публикацию. Синтетические тесты не подтверждают безопасный запуск Vite или Windows.

По умолчанию `materialize` создаёт приватные файлы и каталоги. Для отдельного **нового** delivery в POSIX есть явный `--permission-profile web-readable --acknowledge-world-readable`: файлам назначаются 0644, каталогам 0755, в том числе корню delivery. Это может сделать **все выбранные файлы доступными другим локальным пользователям**: заранее проверьте состав на секреты; по имени обнаружить все секреты нельзя. Права родительских каталогов, ACL, политики системы и конфигурация реального веб-сервера могут препятствовать доступу; режим сам по себе не подтверждает работоспособность сервера или безопасность. Флаг не выполняет сервер и не публикует сайт.

Для этого профиля запись delivery v2 фиксирует hash поддерживаемых POSIX-метаданных; `publish-plan` откажет при изменении прав/uid/gid/mtime или неподдерживаемых видимых xattrs/ACL. Старая запись v1 приватного профиля остаётся совместимой и связывает только содержимое, не метаданные на момент создания. После успешного создания `operation=applied` относится к **созданию delivery**, а статус остаётся `INCOMPLETE` и публикация запрещена; при ошибке после попытки создания — `operation=unknown`, частичная копия сохраняется и может оказаться доступной другим. Тесты назначения прав и mock-переноса выполнялись только на синтетике, не в отдельном системном аккаунте веб-сервера.

## Статический эталон: ограниченная диагностическая копия

`reference-materialize --source source --selection <source/.work/selection.json> --output <source/.work/static-references/id> --json` без исполнения копирует только выбранные в JSON относительные пути из source snapshot. Родительские каталоги добавляются, содержимое выбранной директории не включается автоматически. Исключённые политикой source пути (`.work`, `.env*`, генерируемые файлы), скрытые имена, ссылки и специальные файлы не копируются. Как и в delivery, список выбранных и исключённых файлов нужно просмотреть; имена/содержимое обычных файлов тоже могут содержать секреты. Запись имеет отдельный SHA-256. `reference-inspect --source source --file <reference-record> --sha256 <record-hash> --json` проверяет свежесть source и копии; hash не является доказательством авторства.

Для диагностического прогона подготовленной копии существует `browser-audit-static-md --source source --site <candidate-root> --reference-record <reference-record> --reference-sha256 <record-hash> --acknowledge-browser-code --json`. Он запускает временный встроенный read-only сервер для копии и браузер; не запускает npm, Vite или серверный код из экспорта и не меняет `source/` вне `.work/`. Это только static HTML/resources: SPA с динамическими маршрутами, сборка и API автоматически не поддерживаются. Выбранные HTML и JavaScript **исполняются в браузере**. Команда не предоставляет ОС-изоляцию, Playwright routing не заменяет sandbox; запускайте её только в подходящей изолированной среде или после согласованной оценки риска доверенного содержимого. Флаг — явное подтверждение оператора, а не доказательство безопасности. Привязка copy/source проверяется до и после прогона и при `run-seal`/`run-inspect`, но происхождение исполнения, независимость эталона и качество всё равно не доказаны, `eligible=false`.

## Записи запусков и сводка готовности

После `browser-audit-md` можно сохранить проверяемый **отпечаток диагностического прогона**, не выдавая его за доказательство происхождения. Вычислите SHA-256 байтов созданного `summary.json` и выполните `run-seal --source source --site <candidate-root> --audit <source/.work/audits-md/id> --summary-sha256 <sha256> --json`. Команда возвращает новый `source/.work/run-records/*.json` и SHA-256 его байтов: сохраните этот hash отдельно, чтобы обнаружить изменение записи. В запись входят hashes source, очереди, требований, сценариев и артефактов, конфигурация, время, версия браузера, fingerprint Python/зависимостей/локальных модулей tools и сводка coverage. Если этот инструментарий изменился, запись считается устаревшей; старый запуск без toolchain fingerprint нужно повторить. Скриншоты и отчёты могут содержать личные сведения.

`run-inspect --source source --site <candidate-root> --file <record.json> --sha256 <record-hash> --json` сверяет запись и все артефакты, а также актуальную очередь, сценарии, исходник и candidate. `readiness --source source --site <candidate-root> --run-record <record.json> --run-sha256 <record-hash> --manual-record <attestation.json> --manual-sha256 <attestation-hash> --json` составляет матрицу обязательных проверок и список блокировок; обе пары параметров необязательны. Те же пары можно передать в `publish-plan`: свежесть записей участвует в повторном вычислении плана, но не открывает apply.

Это хеширование обнаруживает изменения только относительно сохранённого hash; оно **не доказывает**, кто произвёл запуск, что внешний сервер соответствует исходнику, что среда изолирована, или что ручное заявление достоверно. Даже поддельный `pass` в записанном отчёте остаётся `review`; `eligible=false`. Результат не является автоматической приёмкой и не разрешает публикацию. Записи и внешняя проверка должны быть защищены от некооперативных писателей отдельно.

## Windows preview.bat

`preview.bat` — вспомогательный Windows-сценарий, **не изоляция и не проверенный эталон**: он выполняет npm build/preview и конфиги проекта, изменяет `source/node_modules`, `source/build` и `source/.cache`. Сценарий предупреждает о риске и отказывается открывать уже занятый порт; проверка порта всё ещё не доказывает принадлежность listener при гонках. Используйте только доверенный экспорт в подходящей среде. Изменения скрипта и Windows в этом окружении не запускались.

## Диагностика профилей

### Статический pnpm lock v9 и кэш tarball

`pnpm-lock-inventory --source <source> [--project <относительный-корень>] --json` только читает `package.json` и `pnpm-lock.yaml` версии 9.0, проверяет ограниченный формат registry-resolutions с SHA-512, совпадение root specifier и наличие записанных рёбер graph/snapshots. Пакеты, snapshots и достижимые узлы подсчитываются; сеть и код проекта не используются. Неизвестные форматы, YAML aliases, повторные ключи, локальные/git зависимости и workspace блокируются. Проверка не является pnpm resolver, frozen install или проверкой semver, peer resolution, overrides, platform/libc, безопасности архива и runtime.

`pnpm-lock-cache --source <source> [--project <корень>] [--allow-registry-network] --json` проверяет content-addressed `.work/npm-tar-cache` по SHA-512 или, только с явным флагом сети, скачивает отсутствующие архивы с `registry.npmjs.org` без прокси и redirect. По умолчанию в кэш включаются **все** metadata-пакеты lock, даже необязательные и несовместимые с текущей платформой; возможна значительная загрузка. Опция `--selected-platform` ограничивает загрузку консервативно выбранными достижимыми пакетами Linux x86_64/glibc для описанного ниже дерева; она не воспроизводит полную семантику pnpm. Файлы проверяются по lock, но не распаковываются; проект, npm, pnpm и lifecycle-скрипты не запускаются. При сбое после изменения кэша возвращается `operation=unknown`, файлы остаются для проверки. Сам кэш не подготавливает `node_modules`, peer topology или native bindings и не разрешает запуск и публикацию. Разрешён только ограниченный lock v9 с registry integrity; приватные registry/workspaces не поддерживаются.

### Экспериментальное pnpm-shaped дерево

`pnpm-tree-prepare --source <source> --project . --output <source/.work/pnpm-deps/новый-id> --json` создаёт отдельное дерево из **уже проверяемых offline** архивов `.work/npm-tar-cache`; загрузки здесь нет. Поддерживается Linux x86_64/glibc и ограниченный lock v9, неподходящие опциональные OS/CPU/libc snapshots пропускаются, несовместимая обязательная зависимость блокирует подготовку. Каждому snapshot, включая peer-контекст, соответствует отдельный каталог; ссылки графа относительные и ограничены созданным деревом. Скрипты, pnpm/npm и проект не выполняются; `.bin` не создаётся. При сбое после начала записи — `operation=unknown`, частичное дерево сохраняется.

`pnpm-tree-inspect --source <source> --file <record> --sha256 <record-hash> --json` сверяет source snapshot и содержимое дерева, пути и цели внутренних ссылок и execute bits файлов. Проверка относительная: hash записи не доказывает происхождение, внешние редакторы могут вызвать гонки. Архивы не распаковываются в ОС-песочнице; существующие ограничения по символическим ссылкам и составу tarball могут отвергать корректные пакеты.

Это **не `pnpm install`**: полный resolver, semver/peer satisfaction, workspaces, overrides, native bindings, lifecycle-скрипты, совместимость среды и сетевые/системные ограничения не подтверждены. Настоящий пользовательский pnpm-проект этим не запускался. Синтетическая фикстура React/Vite с lock, сгенерированным pnpm 10.34.3 без установки и scripts, прошла отдельный изоляционный опыт, что не является доказательством безопасности или публикационной приёмкой.

### Экспериментальная подготовка npm lock v3

`npm-lock-plan --source <source> [--project <относительный-корень>] --json` только разбирает `package.json` и npm `package-lock.json` версии 3. `npm-lock-prepare --source <source> --project . --output <source/.work/npm-deps/новый-id> [--allow-registry-network] --json` подготавливает отдельное дерево `node_modules` по этому lock. Без флага сети использует лишь ранее заполненный кэш `.work/npm-tar-cache`; с флагом скачивает HTTPS tarballs только с `registry.npmjs.org`, без прокси/перенаправлений, сверяет SHA-512 и никогда не запускает npm или lifecycle-скрипты. Запись и snapshot дерева сохраняются отдельно; `npm-lock-inspect --source <source> --file <запись> --sha256 <hash> --json` проверяет изменение source и дерева. Это относительная целостность, не доверенное evidence и не разрешение на запуск или публикацию. При сбое после записи кэша или начала создания результата возвращается `operation=unknown`; кэш и частичный каталог сохраняются для проверки.

Это **узкий эксперимент**, не эквивалент `npm ci`: только Linux x86_64, lock v3, registry tarballs с SHA-512, без workspaces, links, `.bin` и lifecycle-скриптов; не проверяются полная семантика npm, совместимость библиотек или безопасность содержимого. Возможны отказы для корректных пакетов. Имеются ограничения размера/числа файлов, но это не проверенная песочница для вредоносных архивов или защиты от гонок внешних писателей. Реальный экспорт в `source/` использует `pnpm-lock.yaml`: доступны описанные выше ограниченные инвентарь, кэш и экспериментальное дерево, но не подтверждённые установка или запуск. Не преобразовывать lock и не выполнять проект ради обхода ограничения.

`python -m tools.cli runner-profiles --json` сообщает доступную политику, не исполняя проект. Отдельный `runner-synthetic --allow-fixture-registry-network --timeout 120 --json` управляет только встроенной синтетической фикстурой, а не пользовательским source; это не production runner. Таймаут, лимит лога и границы очистки описаны в [runner-spike.md](runner-spike.md). На Linux read-only `resource_controls` разрешает текущую cgroup v2 относительно mountinfo, показывает доступные и включённые контроллеры, тип, наличие `cgroup.kill` и подсказки о правах; ошибки возвращают `unknown`. `rw` mount, видимые controllers или `os.access` не доказывают делегирование, корректность лимитов, возможность очистки дерева или квоту: проверочных мутаций нет, `delegation_verified` и `aggregate_limits_verified` всегда false, а квота unknown. Сведения содержат локальные пути; инструмент не защищает от недоверенной подмены proc/mount. `managed-isolated` и запуск произвольного Vite как `managed-local` пока недоступны; доступен ограниченный `managed-static-diagnostic` с описанными выше рисками и явным подтверждением. Внешние URL не имеют подтверждённого происхождения. Отдельный воспроизводимый Linux-опыт на собственных синтетических React/Vite фикстурах и его ограничения описаны в [runner-spike.md](runner-spike.md); это не разрешение запускать недоверенный экспорт.
