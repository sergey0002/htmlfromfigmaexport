## 1. Короткий вывод

Для сценария «положил React-экспорт в `source/`, написал агенту “верстай”, получил проверенную `vanilla/`» целесообразно не искать один волшебный конвертер, а собрать небольшой локальный конвейер:

1. **Сначала использовать имеющийся Python Playwright**: восстановить зависимости, исправить и обобщить просмотр, снимки и проверки из `.doc/scripts/` для разных экспортов.
2. **Сначала проверить имеющийся `check_vanilla.py`**: убрать привязку к примеру, исправить ошибки и выявить пробелы. Если нужна полноценная проверка структуры HTML, рассмотреть **HTML-validate** как дополнение, а не автоматически ставить второй валидатор.
3. **axe-core, Stylelint и Lighthouse** — дополнительные проверки, которые стоит подключать по отдельности, если они закрывают реальные пробелы; доступность также требует ручной проверки.
4. **Playwright Test + pixelmatch** или **BackstopJS** — альтернативы существующему Python-сравнению, если его недостаточно; не устанавливать обе без доказанной необходимости. **Babel parser** — возможное улучшение анализа JSX/TSX, не полноценный конвертер.
5. Если у пользователя есть исходный файл Figma, отдельно рассмотреть **официальный Figma MCP** или генератор кода из макета. Они дополняют, но не заменяют обработку папки `source/`.

Это рекомендации по исследованной документации, **не внедрённые в проект зависимости**. В ходе этого исследования ни один кандидат не устанавливался и не сравнивался на настоящем макете; заявленные качества — возможности из документации, а не результаты собственного benchmark. Для подтверждения нужен PoC по разделу 8.

## 2. Главный вопрос: можно ли автоматически превратить React в готовый HTML?

Готовые средства позволяют получить промежуточную разметку, но не гарантируют качественную самостоятельную вёрстку:

- **React `renderToStaticMarkup`** превращает React-дерево в начальную HTML-строку, не требует React в браузере для отображения статического содержимого. Однако эта разметка неинтерактивна и не поддерживает гидратацию; при Suspense может вывести fallback [1](https://react.dev/reference/react-dom/server/renderToStaticMarkup). Не все экспорты можно просто отрендерить на сервере: исходник может ожидать `window`, DOM, маршрутизатор, API или browser-only библиотеки. CSS, ресурсы и состояния нужно обрабатывать отдельно.
- **Снимок DOM в Playwright** помогает увидеть фактически отрендеренный HTML в текущем состоянии браузера. Это полезный материал агенту, но снимок не содержит логику обработчиков React и не гарантирует сохранение реактивности, всех маршрутов, скрытых состояний, стилей или зависимых ресурсов.
- **Astro с React-интеграцией** может по умолчанию отрендерить framework-компоненты как HTML на сервере, а `client:*` включает клиентскую гидратацию [1](https://docs.astro.build/en/guides/framework-components/). Если гидратировать React-компонент, в браузер попадёт его framework runtime: это противоречит текущей цели «без React в результате». Использовать как альтернативную архитектуру только если владелец изменит требование; не считать Astro автоматическим переводчиком интерактивного React в vanilla JS.
- **Сборка Tailwind** превращает утилиты в обычный CSS-файл без Tailwind CDN/runtime, но сохраняет utility-классы в HTML. Это допустимый технический компромисс для быстрого прототипа, если владелец принимает такой стиль разметки; это ещё не то же самое, что аккуратный семантический CSS. Компилятор сканирует исходники как текст и не понимает произвольно конструируемые имена классов; поэтому важны исходные конфиги, корректная область сканирования и проверка интерактивных состояний [1](https://tailwindcss.com/docs/detecting-classes-in-source-files).

**Рекомендация:** на первом этапе агент делает вёрстку и переносит поведение, используя DOM/исходный CSS как подсказку. Впоследствии можно автоматизировать распознаваемые простые шаблоны, но неизвестные конструкции должны быть обозначены как ограничения, а не молча потеряны.

## 3. Кандидаты для просмотра и pixel-perfect сравнения

### 3.1. Playwright — базовый инструмент

**Назначение:** запуск Chromium/Firefox/WebKit, два независимых URL, смена viewport, клики, состояние меню/табов, локаторы, снимки экрана, чтение DOM и computed styles. `@playwright/test` умеет сохранять и сравнивать снимки с baseline через `toHaveScreenshot`; документация отдельно предупреждает, что окружение и шрифты влияют на результат [1](https://playwright.dev/docs/test-snapshots).

**Как применить:**

- Открывать живой React из `source/` и кандидат из staging. На обеих страницах выставлять одинаковый viewport, масштаб, язык, состояние, шрифты и действия. Проверять загрузку и ошибки отдельно.
- Получать полный снимок, а для интересующих секций — отдельные снимки. Дополнительно измерять границы элементов, тексты и количество элементов; проверять открытое меню и другие состояния, а не только первый экран.
- Отчёты и скриншоты складывать в `.work/`, не в `vanilla/`. Для среды пользователя использовать безопасные preview URL, а браузеру внутри sandbox — внутренние адреса запущенных сервисов.
- Установить версии пакетов и браузера в отдельном инструментарии проекта, не в каждом новом входном экспорте. Для Python можно использовать уже знакомый Python Playwright; для единого Node-стека — `@playwright/test`. Выбирать **один** основной стек, не дублировать одинаковые проверки.

**Важное различие:** `toHaveScreenshot` сравнивает страницу с сохранённым эталонным файлом, а не просто два URL на лету. Поэтому либо сначала отдельно снимать React-baseline с проверкой качества и использовать его при тесте HTML, либо писать небольшую обвязку для парных снимков и сравнивать их библиотекой pixelmatch. Baseline должен быть создан **из текущего источника**, привязан к его отпечатку и viewport; нельзя автоматически принять результат `vanilla/` за эталон. Отсутствие базового снимка или незагруженный источник — `blocked`, не PASS.

**Минусы:** браузеры нужно отдельно установить; разные ОС, версии, шрифты и анимации дают шум. Нужны собственные правила ожидания загрузки, маршрутов, сопоставления элементов и отчётности. Это инструмент контроля, а не генератор HTML.

### 3.2. pixelmatch — сравнение двух изображений

**Назначение:** сравнивать PNG-пары и создавать diff с учётом антиалиасинга; это же семейство алгоритмов используется Playwright Test [1](https://playwright.dev/docs/test-snapshots). Самостоятельный `pixelmatch` полезен именно для **двух живых URL**: Playwright снимает React и HTML в одном окружении, затем обвязка сравнивает изображения и сообщает результат [1](https://github.com/mapbox/pixelmatch).

**На что обратить внимание:** библиотека принимает изображения одинаковых размеров, поэтому несовпадение размеров нужно сначала отдельно обнаружить и отразить в отчёте, а не молча обрезать. `threshold` — чувствительность к отличию цвета одного пикселя, а не допустимый процент отличающихся пикселей; процент рассчитывается отдельно. Пороги и игнорирование сглаживания могут скрывать мелкие дефекты. Дополнительно потребуются чтение/запись PNG (например, `pngjs`) и проверка взаимодействий. Если используем только `toHaveScreenshot`, отдельное прямое подключение pixelmatch может быть не нужно.

**Приоритет:** высокий, если выбран вариант парного сравнения вместо snapshot-файлов; иначе не добавлять отдельно.

### 3.3. BackstopJS — готовая альтернатива обвязке

**Назначение:** конфигурируемое визуальное сравнение с HTML-отчётом. Поддерживает отдельные `referenceUrl` и `url`, viewport, интерактивные скрипты и работу с baseline [1](https://github.com/garris/backstopjs). Для этого проекта эталонный URL — React, целевой URL — staging-верстка. После регистрации эталона выполняется сравнение результата.

**Плюсы:** готовый интерактивный отчёт, обзор diff, конфигурация сценариев, возможность выбирать блоки и размеры вместо разработки всего с нуля. Это особенно полезно, если пользователю нужен визуальный интерфейс сравнения.

**Минусы:** сценарии и корректные состояния всё равно надо описывать/генерировать; baseline нужно изолировать между экспортами. `reference`/`approve` управляют эталонами и не должны автоматически подтверждать ошибочный результат. В официальном README на дату исследования есть просьба найти нового maintainer/owner — риск сопровождения, который стоит учитывать. Это не проверено в данном окружении. Также нужно отдельно проверять отсутствие ресурсов, соответствие DOM и работу UX; визуальное сравнение само по себе недостаточно.

**Выбор:** сначала короткий PoC **BackstopJS vs Playwright Test + pixelmatch**. Если готовый отчёт существенно удобнее и риски сопровождения приемлемы — выбрать BackstopJS. Иначе сохранить минимальный Playwright-стек. Не пытаться сохранить прежние спорт-селекторы как универсальные.

### 3.4. Облачные варианты: Percy и Chromatic

[Percy](https://www.browserstack.com/percy) и [Chromatic](https://www.chromatic.com/) — варианты для командного визуального ревью и CI. Они могут быть полезны, если проектов и проверок станет много, понадобятся история, согласование отличий и совместная работа. Chromatic особенно логичен при наличии Storybook; для сценария произвольной папки с React это не обязательное основание вводить Storybook.

Минусы: внешний сервис, учётная запись, квоты/условия и возможная передача чувствительных скриншотов или данных за пределы рабочей среды. Цены и ограничения часто меняются — проверять по официальным страницам перед выбором, в этом исследовании актуальные тарифы и условия не подтверждались. Начинать с локальных инструментов; облако подключать только по желанию владельца и после проверки приватности.

## 4. Доступность, валидация и качество

### 4.1. axe-core + Playwright

`@axe-core/playwright` запускает автоматический анализ текущего состояния страницы в браузере; например, можно отдельно проверить страницу до и после открытия меню. Playwright подчёркивает, что автоматические проверки находят только часть проблем доступности и не заменяют ручные [1](https://playwright.dev/docs/accessibility-testing).

**Интеграция:** проверять все маршруты и важные раскрытые состояния. В отчёт включать violations и элементы, требующие ручной проверки; затем пройти страницу клавиатурой, проверить фокус, осмысленность названий, контраст и при необходимости скринридер. Не обещать WCAG-соответствие только по зелёному тесту. Если эталон сам недоступен, исправлять результат аккуратно: сохранять дизайн, но не копировать заведомо неработающее управление.

**Приоритет:** высокий. Нужен npm-пакет и браузер, но не внешний SaaS.

### 4.2. HTML-validate / Nu Html Checker

[HTML-validate](https://html-validate.org/) — локальный HTML-валидатор для документов и фрагментов; помогает находить неверную вложенность, устаревшие элементы и часть формальных ошибок [1](https://html-validate.org/). Хорошо подходит для проверки каждой HTML-страницы в `vanilla/` без отправки клиентского кода наружу.

[Nu Html Checker](https://github.com/validator/validator) — дополнительный вариант проверки корректности HTML, доступен для локального запуска; при самостоятельном развёртывании нужны его runtime и управление версиями. Выбрать один основной валидатор, второй подключать только если найдены полезные отличия. Ни один не гарантирует визуал, UX или истинность SEO-метаданных.

**Приоритет:** HTML-validate — высокий; Nu — опционально.

### 4.3. Stylelint и форматирование

[Stylelint](https://stylelint.io/) проверяет ошибки и выбранные соглашения CSS, поддерживает конфигурацию правил. Начинать с небольшого набора правил на реальные ошибки, а не блокировать вёрстку из-за произвольного порядка свойств. Для форматирования можно использовать уже имеющийся в корне `oxfmt` либо выбрать единый другой форматтер после проверки HTML/CSS/JS-поддержки и совместимости; не добавлять несколько форматтеров с конфликтующими правилами.

Линтер не доказывает отсутствие мёртвого CSS и не гарантирует совпадение с макетом. Автоисправления проверять тестами и diff.

### 4.4. Lighthouse / Lighthouse CI

[Lighthouse CI](https://github.com/GoogleChrome/lighthouse-ci) автоматизирует запуски Lighthouse и отчёты; применим к отданным по HTTP страницам `vanilla/`. Отдельно оценивать мобильный и десктопный режимы, повторять нестабильные измерения и записывать окружение. Производительность в виртуализированном CI зависит от среды; высокий балл не заменяет визуальную и функциональную приёмку. SEO-подсказки не дают права выдумывать домен, `canonical` или включать индексацию.

**Приоритет:** после запуска базовых HTML/a11y и браузерной сверки; сначала отчёт/предупреждение, затем согласованные пороги.

## 5. Анализ экспорта и перенос CSS

### 5.1. `@babel/parser` вместо расширения regex-анализатора

[Babel parser](https://babeljs.io/docs/babel-parser) разбирает JavaScript, JSX и TypeScript в AST [1](https://babeljs.io/docs/babel-parser). Для нашего проекта может находить импорты, структуру компонентов, объявления состояния, JSX-атрибуты и обработчики надёжнее регулярных выражений. При необходимости добавить traversal и анализ графа импортов.

**Ограничения:** AST не исполняет код и не знает итогов API, всех значений props, вычисляемых классов и поведения в браузере. Это инвентаризация с указанием мест в коде, не готовый переводчик. Не выполнять исходник только ради получения AST. Брать реальные версии parser/plugins с учётом JSX/TSX и синтаксиса экспорта.

**Приоритет:** средний: сначала Playwright + реальные проверки; затем заменить самые хрупкие regex там, где AST действительно помогает.

### 5.2. Использовать компилятор Tailwind исходного проекта

- Определить **фактическую версию Tailwind и конфиг в экспорте**; v3 и v4 устроены по-разному. При сохранении утилит применять его собственную сборку или совместимый build-инструмент к staging, а не копировать старый корневой CSS.
- Исходный CSS, кастомные шрифты, media/container queries, SVG, CSS-переменные, состояния и assets — часть контракта. Проверять все классы, включая появляющиеся после кликов и из библиотек; расположение `source/` и настройки игнорирования файлов могут потребовать явного задания путей сканирования. Документация Tailwind описывает `@source` и проблему динамических имён [1](https://tailwindcss.com/docs/detecting-classes-in-source-files).
- CSS, сгенерированный Tailwind, — обычный CSS, но разметка останется utility-heavy. Для чистой долговечной вёрстки агент может перевести ключевые блоки в понятные классы и проверить результат; нельзя заявлять, что это произошло автоматически после компиляции.
- **PurgeCSS** можно исследовать как необязательное средство уменьшения CSS, но его документация предупреждает о динамически создаваемых классах и предлагает safelist [1](https://www.purgecss.com/safelisting). Не запускать агрессивную чистку без тестирования всех состояний: можно удалить работающие правила, шрифты, keyframes или переменные. На старте это скорее риск, чем необходимость.

### 5.3. Оптимизация ассетов

Использовать подходящие инструменты только при необходимости и с проверкой лицензий/прозрачности: оптимизация SVG/растровых изображений может изменить изображение, crop или качество. Сначала сохранить оригиналы; сравнить размеры, визуал и альфа-канал до и после, не перекодировать автоматически все изображения. Проверять права на шрифты и возможность self-host; не скачивать/публиковать их без разрешения.

## 6. Если доступен исходный файл Figma

### 6.1. Официальный Figma MCP

[Figma MCP Server Guide](https://github.com/figma/mcp-server-guide) описывает получение design context, переменных/стилей и скриншотов выбранного узла; это дополнительный контекст для агента и способ свериться непосредственно с макетом [1](https://github.com/figma/mcp-server-guide). Особенно полезно, если React-экспорт уже отличается от дизайна либо в нём потеряны названия слоёв/значения токенов.

Нужны права доступа к конкретному файлу, совместимый MCP-клиент и соответствующие условия Figma; лимиты и тарифы необходимо проверить на момент подключения. Наличие MCP в конкретной среде Arena в этом исследовании не проверялось. Перед отправкой дизайна во внешний сервис нужно убедиться в разрешениях и условиях конфиденциальности. Локальная папка React остаётся основным входом, MCP — **опция**, не обязательная зависимость.

### 6.2. Builder.io Visual Copilot

Производитель заявляет экспорт из **Figma-дизайна** в HTML и разные framework-форматы, в том числе со стилями CSS/Tailwind [1](https://www.builder.io/blog/figma-to-code-visual-copilot). Это потенциально интересный обходной маршрут, если исходный макет доступен и можно получить HTML напрямую, минуя React.

**Не путать с задачей проекта:** инструмент работает от Figma-дизайна, а не является проверенным преобразователем произвольной папки React → чистый HTML. Маркетинговые заявления о готовности и pixel-perfect не подтверждены нашим тестом; нужно отдельно проверять семантику, адаптив, поведение, размер, права на assets, стоимость и отправку данных. Рассматривать как сравнительный вариант, не обязательную основу проекта.

## 8. Проверочный PoC до окончательного выбора

Ниже — план эксперимента, не заявленные результаты.

1. Взять две **не связанные друг с другом** небольшие React-фикстуры: одна с меню/раскрытием, другая с сеткой/табами; добавить отдельные страницы, SVG, локальные шрифты и Tailwind-брейкпоинты. Иметь разрешение на использование всех ресурсов. Подготовить заведомо правильную и намеренно испорченную `vanilla/`.
2. Зафиксировать Node, версии библиотек и браузера, ОС/образ, viewport/DSF, шрифты и время. Проверить загрузку ресурсов и работу исходников до съёмки; нет Chromium/LFS/шрифта — `blocked`, не PASS.
3. Сравнить Playwright snapshots/парный pixelmatch и BackstopJS по одинаковым маршрутам и состояниям: старт, раскрытая карточка, мобильное меню, hover/focus; ширины 390, 768, 1024, 1440 и соседние точки около реальных брейкпоинтов.
4. Внести контролируемые дефекты: ошибка текста, сдвиг на несколько CSS-пикселей, неверная высота, пропущенная картинка, неправильный breakpoint, сломанный клик, отсутствие секции, пустая страница и разные размеры. Измерить, что выявляется каждой проверкой, а что нет. Проверить отсутствие ложного PASS при пропусках.
5. Замерить время установки/прогона, размер зависимостей, качество и удобство отчёта, стабильность повторных запусков, работу Windows/Linux и preview-host. Выяснить, можно ли корректно проверить экспорт с интернет-зависимым шрифтом без нарушения ограничений среды.
6. Добавить HTML-validate/axe и сравнить найденные ошибки с ручным keyboard-check; записать не только число ошибок, но и ложные срабатывания/непокрытые состояния. По результату выбрать минимальный стек, а не подключать все инструменты сразу.
7. Оформить решение: версии/лицензии/системные зависимости, конфиденциальность, границы поддержки, команды, артефакты, критерии PASS/FAIL/blocked и план отката. Только после этого менять существующие скрипты и `AGENTS.md`.

## 9. Условия безопасности и эксплуатации

- `source/` — чужой исполняемый код: npm lifecycle scripts, Vite plugins и сторонние зависимости могут выполнять команды. Перед запуском изучать manifest и конфиг, применять изолированную среду, ограниченные права и сеть; не передавать туда секреты. `--ignore-scripts` может ломать некоторые зависимости и сам по себе не делает выполнение приложения безопасным.
- Не публиковать скриншоты и DOM в облачных сервисах без разрешения. Разделять внешние и локальные URL, приватные данные скрывать только согласованно, чтобы не скрыть существенные дефекты.
- Устанавливать инструменты через lock-файл и проверенные источники; фиксировать браузер и совместимость Node, периодически проверять обновления/лицензии. Потребление диска для снимков и браузеров учитывать отдельно от итоговой поставки.
- Исследование не проверяет актуальный доступ к платным сервисам, внешним шрифтам и Figma MCP в этой среде. В прошлом обследовании браузерные тесты были заблокированы отсутствием Playwright/Chromium; наличие реальных LFS-объектов также требуется проверить перед визуальной приёмкой.
