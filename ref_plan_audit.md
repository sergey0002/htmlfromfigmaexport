# Аудит плана `ref_plan.md` перед реализацией

Дата: 2026-11-27. Основание проверки — **текущий код и тесты рабочего дерева**, а не описание намерений в прежних документах. План исправлен и дополнен в [ref_plan.md](ref_plan.md); исходный код, манифест и инструкции в ходе этой проверки не менялись.

## 1. Итог

Направление плана верное: детерминированные операции передаются CLI, смысловые решения — агенту; сохранены многостраничность, самостоятельные HTML и необходимость восстановить автоматический эталон. Однако исходная редакция была недостаточно точна для безопасной реализации: в ней отсутствовали единый проверяемый снимок поставки, конкретный контракт миграции и переходных интерфейсов, модель допустимости доказательств и технически реализуемая топология изоляции.

**Решение:** план доработан, а не просто одобрен. В нём уточнены схемы, инварианты, очередность, переходный fail-closed режим, evidence, воспроизводимые регрессии и конкретные рабочие пакеты. Предлагаемые новые команды/форматы в плане явно помечены как **целевые**; сегодня их ещё нет. Технический результат рефакторинга и Windows/изоляция не объявлены выполненными.

Дополнительно выявлен и воспроизведён новый P0-дефект исходного кода: текущая сериализация fingerprint допускает одинаковый хеш для двух разных деревьев без взлома SHA-256 (§3.1). Добавлены регрессия R10 и конкретная спецификация snapshot v2.

## 3. Результаты аудита и исправления плана

### 3.1. P0 — fingerprint имеет неоднозначное представление

**Код:** `tools/core.py:46–55` хеширует последовательность `имя + NUL + содержимое + NUL`. Содержимое бинарного файла может содержать NUL, а длина каждого поля не указывается.

**Воспроизведено:** одно дерево с файлом `a = b'1\0b\x002'` и другое с файлами `a = b'1'`, `b = b'2'` дают один и тот же `fingerprint`. На вход SHA-256 поступает идентичная последовательность; криптографическая коллизия не требуется.

Самостоятельное неразрушающее воспроизведение из корня репозитория:

```bash
python3 - <<'PY'
from pathlib import Path
from tempfile import TemporaryDirectory
from tools.core import fingerprint
with TemporaryDirectory() as tmp:
    root = Path(tmp)
    first, second = root / 'first', root / 'second'
    first.mkdir(); second.mkdir()
    (first / 'a').write_bytes(b'1\0b\x002')
    (second / 'a').write_bytes(b'1')
    (second / 'b').write_bytes(b'2')
    print(fingerprint(first) == fingerprint(second))  # сейчас True
PY
```

**Исправление плана:** R10 и §17: доменно-разделённая length-framed сериализация записей, отдельные source/delivery policy IDs и hash каждого файла, уникальная версия и независимые тест-векторы; v1 hashes не переименовывать в v2 и не считать прежние доказательства актуальными. Кроме этого, остаётся отдельно ранее установленное расхождение охвата копируемого дерева и fingerprint.

### 3.2. P0 — неполное соответствие проверенного и переносимого дерева

**Код:** `tools/core.py:17–43` исключает каталоги по имени, а `tools/lifecycle.py:154–165` копирует всё дерево `shutil.copytree`. План ранее предлагал выбрать исключения в `publish plan` уже после проверки staging, что могло привести к проверке одного набора и переносу другого.

**Исправление:** §16 устанавливает последовательность: рабочий staging → явный отбор → materialized delivery snapshot → static/browser/manual проверки **этого** набора → plan → apply именно этого набора → финальная проверка. Исключения показываются до проверок, любое изменение требует нового snapshot; полный состав конечной копии сверяется. Hash состава сам по себе не доказывает визуальную проверку каждого файла — покрытие учитывается отдельно.

### 3.3. P0 — статусы evidence и возможность подделки

**Код:** `tools/lifecycle.py:56–103` принимает browser JSON по структуре, для manual достаточно непустого текста, для static повторно запускается `check_manifest`, но поданный файл не сверяется с этим результатом. `tests/test_multipage_workflow.py:78–91` сам создаёт упрощённый browser JSON, который принимается как `checked`. `publish` опирается на записанные проверки (`lifecycle.py:132–145`).

**Недостаток плана:** различение trust и hashes упомянуто, но не было однозначно сказано, что локальный пользователь с правами записи на все файлы может изменить и отчёт, и реестр. Ввод нового `run_id` этого не устраняет.

**Исправление:** §20.1 и таблица §19: автоматическое исполнение регистрируется в том же контролируемом run, импорт — `unverified`, manual — структурированное утверждение, а не автоматическое свидетельство. Происхождение внешнего эталона фиксируется отдельно. Схема защищает от случайного смешения/импорта, но не обещает защиты от владельца рабочей среды; для независимой аттестации нужна отдельная защищённая граница доверия. Указаны реальные критерии eligibility и перенос старых проверок в stale/unverified.

### 3.4. P0 — переход может оставить старый небезопасный путь активным

**Код:** текущие `cli.py:92–95` вызывают существующий `record` и `publish`; `publish` использует v1 `checked`. План перечислял новые версии поэтапно, но не определял, что делать между этапами.

**Исправление:** §19 и WP2/WP7: до готовности новой связки snapshot/requirements/evidence/promotion старые ветки, способные принять непроверенный `checked` или выполнить перенос, переводятся в явный fail-closed режим. Диагностические команды продолжают работать. Старый `publish --site` не делает apply по умолчанию: предлагается выдавать только plan и подробное сообщение о новом контракте. Изменение совместимости должно быть задокументировано и протестировано.

### 3.5. P0 — ошибка отчёта после мутации требует отдельного исхода

**Код:** `tools/cli.py:92–95,154–169`: `publish` выполняется до валидации `--report`. При невалидном пути получается `BLOCKED` и код 3, хотя каталог уже может быть установлен. Этот случай был воспроизведён в [ref_audit.md](ref_audit.md).

**Исправление:** предварительная проверка и резервация, а также отдельные `operation`/`report_result` и JSON envelope даже при позднем IO-сбое (§5.2, §19). Пояснено ограничение: при недоступных stdout и журнале нельзя обещать сохранение отчёта. План включает негативные и конкурентные тесты.

### 3.6. P1 — исходный план не задавал реальное строение и миграцию v1

**Код:** `tools/queue.py:37–65` валидирует v1; `discovery.unresolved` — список произвольных заметок и не блокирует `confirmed`, `unresolved_links` — отдельные объекты с обязательным решением. `queue.py:154–161` при новом source сбрасывает checks в `not_run`, но сохраняет page confirmations. `source/.work/manifest.json` содержит также `fingerprint_version`, `hints`, page `evidence`, `issues` и 67 состояний.

**Воспроизведено:** на копии данных в памяти можно подтвердить discovery при сохранённых свободных заметках, если структурированные `unresolved_links` решены. Это соответствует текущему коду, но означало, что требование плана «разобрать все неопределённости» без типизации могло заставить трактовать обычное предупреждение как блокирующий вопрос.

**Исправление:** §18: явные типы `decision_required|limitation|info`, правила переходов и обязательные поля, сохранение фактической глобальной неподтверждённости, всех ID/состояний/заметок/unknown fields, `dry-run`, backup, CAS и миграция проверок как исторических. Добавлен R11. Полнота по-прежнему определяется агентом, а не количеством найденных AST-узлов.

### 3.7. P1 — невозможно однозначно вычислить requirements hash

**Код:** `tools/lifecycle.py:96–124` связывает проверки с source/site/report, но не с набором требуемых states/scenario bytes; вследствие этого ранее воспроизведён R1. `tools/screen_audit.py:31–33` резервирует имя `initial` и `load_scenarios()` не принимает его как пользовательское имя.

**Недостаток плана:** не определял состав requirements hash и мог создать цикл: запись проверки меняет manifest → hash меняется → проверка сразу stale. Также матрица «все алиасы × все состояния × все размеры» была чрезмерной и не учитывала применимость.

**Исправление:** §17–18 и §20.3: hash включает семантические требования и исключает work status, время и results; `initial` формируется отдельно, сценарии и обязательные viewport задаются явно; матрица строится по подтверждённым применимым комбинациям. Первоначально консервативно устаревают все проверки, пока зависимость не доказана.

### 3.8. P1 — ОС-изоляция и сеть описаны без реализуемой топологии

**Код:** сегодня `tools/audit_runner.py:82–89` не запускает React, `browser-audit-site` обслуживает candidate, а `screen_audit.py:150,181–196` работает с loopback URL и перехватом запросов. Старый runner в `7c5798c` применял копию и урезанный environment, не ограничения ОС. `preview.bat:86–107` запускает сборку и preview в исходном `source/`.

**Недостаток плана:** идея изолированного network namespace не уточняла, как Playwright снаружи увидит server внутри namespace, а режим пользовательского долгоживущего preview мог быть смешан с коротким CLI-run. Также выбор порта не может гарантироваться без соответствующего механизма наследования сокета.

**Исправление:** §20.2: два технических варианта — весь процесс аудита в одной ограниченной среде либо ограниченный прокси; отдельно разрешение registry на стадии установки и сеть приложения, временный audit и долгоживущий Arena preview. Managed-local допускается после явной оценки пригодности среды, но не называется isolated; отсутствие Docker само по себе не блокирует работу. PID/port ownership и race проверяются в пределах возможностей ОС, обещание абсолютной гарантии убрано. Интеграционная проверка Linux и отдельный реальный Windows-run обязательны для соответствующих заявлений.

### 3.9. P1 — сканер фактов, статический HTML и прежние тесты конфликтуют

**Код:** `tools/discovery.py:62–76,99–108,127–183` без tree-sitter вообще возвращает до HTML-обхода, выводит кандидат `/`, угадывает hash, маршруты и output. `tests/test_multipage_workflow.py::test_tsx_discovers_router_branches_dynamic_array_and_unresolved` явно ждёт кандидаты по эвристикам; `test_static_multipage_and_ambiguous_output` тоже ждёт страницы, а не факты.

**Исправление:** §6 и WP4: HTML-факты обрабатываются независимо от доступности tree-sitter, а отсутствие JS parser отражается как неполный охват. Старые тесты меняются **вместе** с публичным контрактом на проверку фактов/негативных случаев, а не оставляются бессмысленно падающими. Удаление старых candidate-эвристик не должно удалять человеческие решения из существующего v1 manifest. Этот конкретный parser-fallback дополнительно включён ниже в план как отдельный критерий.

### 3.10. P1 — политика недостающих ресурсов и тесты

**Код и docs:** `AGENTS.md:12` предписывает отсутствующие файлы/LFS показывать как warnings и продолжать; `tools/core.py:189–199,218–219` так и делает; `tests/test_tools.py::test_missing_files_are_only_warnings_and_printed_by_cli` проверяет это явно. При этом `record-check` для браузера требует отсутствие всех warnings (`tools/lifecycle.py:92`), включая предупреждения, которые могут не означать конкретную недостающую обязательную функцию.

**Исправление:** §8.1 и §20.1 разделяют продолжение работы, классификацию воздействия и eligibility. Инструмент не определяет семантическую обязательность ресурса эвристикой: факты — CLI, роль/допустимый fallback — агент или пользователь. В переходных тестах сохранить доступность статического анализа и явный WARN, добавить раздельные tests обязательного и осознанно необязательного ресурса; не превращать все warnings в необъяснимый общий запрет.

### 3.11. P1 — старые документы могут противоречить новому маршруту

**Код/документация:** `.doc/multipage-implementation-plan.md:17–23` содержит снимок исторического состояния: там говорится, что `.work` не исключается, парных маршрутов нет и browser tests не запускались; текущий код и тесты уже другие. У документа есть статусный абзац, но внутри остаются старые формулировки. `.doc/tools.md:7` обещает Python 3.9+, а установленный `tree-sitter==0.25.2` требует >=3.10. `.doc/tools.md` говорит, что manifest отслеживается Git, тогда как файлы сейчас untracked.

**Исправление:** §10.3–10.4 и WP8 требуют актуализировать точные утверждения на основании состояния после внедрения, явно маркировать исторические разделы и проверить фактические git-правила. Поддержка Python/OS и новые команды заявляются только по реально запущенной матрице. При этом `.figma/` и исторические скрипты не должны без необходимости переписываться.

### 3.12. P1 — критерии для восстановленного запуска были слишком общими

**Код:** `source/package.json` задаёт `dev: vite`, текущий `.mise.toml` — Node 22/pnpm 10.34.3, `source/vite.config.ts:35–47` настраивает host/port через environment. `preview.bat` пишет в `source/node_modules`, `source/build`, `source/.cache` и при занятом 8084 использует текущий listener (`preview.bat:38,86–105,124–128`). Эти свойства не универсальны для других экспортов.

**Исправление:** §7.1–7.4, §20.2 и WP5: явно отделить пользовательский Windows preview, managed reference и isolation backend; рабочая копия в `.work`, сохранение стабильного `.bat` сценария, проверка lock/toolchain, портов/cleanup и actual JS render, отрицательные тесты и реальная Windows-матрица. Не выводить версию Node/pnpm для всех проектов из текущего экспорта, не заявлять Windows реализованной без её тестирования.

### 3.13. P2 — номера ссылок и критерии пакетов

В первой редакции вложенные заголовки нумеровались по номеру этапа, а ссылки использовали номер раздела, из-за чего ссылки и таблица трассировки были неоднозначными. План также не определял конкретный разброс работ по файлам и контрольные точки для частичного безопасного внедрения.

**Исправление:** приведены номера вложенных заголовков и таблица трассировки; добавлены WP0–WP8 с зависимостями, ожидаемыми файлами и критериями. Разделы 16–21 являются конкретизацией и имеют приоритет над общими описаниями.

## 5. Что осталось открытым при начале реализации

1. **Профиль исполнения:** нужно реально измерить границы текущей среды и выбрать реализуемый backend. Если конкретный экспорт нельзя выполнить приемлемо безопасно, честно сообщить блокер; не считать это обоснованием выключить автозапуск для всех проектов.
2. **Windows:** проверка `preview.bat`, поведения процессов и filesystem возможна только в реальной Windows-среде. До неё нельзя считать Windows-совместимость доказанной.
3. **Поддерживаемые версии и библиотечный стек:** выбрать по реальной установке/лицензиям/тестам; в плане зафиксирован нижний предел текущего пакета tree-sitter, но не выдумана проверенная матрица.
4. **Исключения, semantically required resources и доверие к внешнему эталону:** агент оценивает конкретный проект; CLI обеспечивает явную запись и валидацию, а не принимает решение по имени файла или порту.
5. **Качество вёрстки:** две сквозные фикстуры и реальное визуальное ревью являются работой будущей реализации, а не результатом текущего аудита.

План подготовлен как последовательность реализации, но эти условия нельзя объявлять уже выполненными. Этот аудит не производил изменений в программном коде, не выполнял миграцию реального manifest и не создавал `vanilla/`.
