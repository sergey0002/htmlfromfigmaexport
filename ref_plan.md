# Детальный план комплексного рефакторинга Figma → vanilla

Основание: [ref_audit.md](ref_audit.md), включая **раздел 14 с исправлением вывода о запуске React-эталона**. Дата: 2026-11-27. Статус: **план, реализация по этому документу ещё не выполнялась**. После сверки с текущим кодом план уточнён: [отчёт об аудите плана](ref_plan_audit.md). Разделы 16–21 задают конкретный контракт внедрения и имеют приоритет над более общими формулировками выше.

## 1. Цель и границы

Создать универсальный, воспроизводимый и практичный процесс работы агента с новыми Figma-экспортами, в том числе многостраничными: тщательное исследование, явная очередь всех доказанных страниц, пофайловая вёрстка, проверка каждого требуемого маршрута и состояния, безопасное локальное сохранение результата. Восстановить автоматический запуск React/Vite-эталона, который существовал до последних изменений и был отключён; не путать запуск приложения с доказанной ОС-изоляцией.

**Распределение ответственности:** CLI исполняет детерминированную механику и выводит наблюдения; агент определяет смысл страниц/состояний, изучает макет, принимает обоснованные решения, делает вёрстку и оценивает визуальный результат. CLI не угадывает маршруты, алиасы, названия, поведение, страницы или оформление по именам переменных и паттернам. Пользователь принимает решения, которые нельзя надёжно вывести из источника или которые затрагивают его данные/права.

### Непереговорные условия

1. Не менять файлы `source/` за пределами `source/.work/`; все проектные сценарии, отчёты, копии, staging, временные файлы и локальные backup — в `source/.work/`. Учитывать уже существующие незакоммиченные изменения; не откатывать их.
2. Сначала изучить источник и составить полную **подтверждённую агентом** очередь страниц и состояний. Недоказанные и отсутствующие страницы фиксировать отдельно, не придумывать их и не включать как обязательные без решения.
3. Результат — самостоятельный статический `vanilla/`: отдельные HTML-файлы, общие `assets/`, повторяемые размеченные header/footer; `template/header.php` и `template/footer.php` — копии готовых блоков для CMS, не runtime-зависимость сайта. Не выдумывать backend, документы, SEO и поведение.
4. Сохранять визуальное и функциональное качество. Один Chromium достаточен; отсутствие эталона, ресурса, состояния или проверки честно показывать. Автоматический тест не подменяет визуальную и ручную проверку агента.
5. Не удалять и не заменять пользовательские данные без оценки и явного разрешения при риске потери. `publish` — только локальный перенос, не деплой.
6. Не выполнять недоверенный экспорт без оценки риска и пригодности окружения; опасные операции, реальные формы и деплой исключены. Текущая временная копия/`--ignore-scripts` не являются доказательством изоляции.

План охватывает harness, навыки, всю публичную CLI, внутренние модули, документацию, тесты, миграцию и Windows/Linux. Построение текущего 15-страничного сайта **не является заменой** универсального рефакторинга и не входит автоматически в реализацию плана; реальный исходник может использоваться для неразрушающего smoke-теста при соблюдении границ.

## 4. Этап 1 — контракты и границы доверия

### 4.1. Версионированные сущности

Определить схемы в коде и документации; примерные имена ниже — **проектируемый контракт**, не уже доступные поля.

- `SourceSnapshot`: `version`, корень и policy ID, упорядоченные нормализованные относительные пути, типы и SHA-256 файлов, диагностированные пропуски и ошибки. Сканируемые discovery файлы включаются в этот снимок. Не включать содержимое рабочего каталога в source snapshot. Секреты не печатать и не отправлять в отчётах.
- `DeliverySnapshot`: точный полный перечень включённых файлов кандидата, типы, размеры и hash; policy ID и перечень **явно исключённых** путей/причин. Выбранный набор отображается до подтверждения. Копирование и контроль при публикации используют этот же перечень; лишние файлы в копии — ошибка.
- `Fact`: стабильный ID в пределах версии snapshot, язык/тип узла, файл, строки/диапазон, буквальное значение и небольшой контекст; отдельно доступ к исходному фрагменту. Не содержащиеся в снимке/непрочитанные файлы маркировать как пропуск. ID не означает, что факт истинный маршрут.
- `DecisionManifest v2`: проект, source snapshot, ревизия, версии политики, страницы и явные решения по ссылкам/алиасам/состояниям. Стабильный ID страницы не пересчитывать при смене маршрута. Для каждого состояния: ID, обязательность, ссылки на сценарии и viewport; причины решений и ссылки на факты.
- `Run`: run ID, тип, время, фактические source/delivery/requirements/scenario hashes, версии инструментов/браузера, параметры, происхождение эталона, окружение, ограничения, охват, ссылки на локальные артефакты. Значения URL без секретов; полные чувствительные данные не протоколировать.
- `Attestation`: кто и когда сообщил об исполнении, конкретный объект/действия, итог, покрытие и пропуски. Это **утверждение**, а не автоматически подтверждённый факт.

Канонизация hash: конкретный формат и тестовые векторы задаёт §17. Текущий `fingerprint` неоднозначен даже без криптографической коллизии (см. R10), поэтому новая версия обязательна. Старые отпечатки не пересчитываются как эквивалентные.

### 4.2. Статусы и совместимость

Разделить:

- `execution`: completed / blocked / error;
- `coverage`: complete / partial / unknown и фактические счётчики по страницам, маршрутам, viewport, состояниям, assertions;
- `outcome`: pass / fail / review / not_evaluated;
- `freshness`: current / stale / unknown;
- `reference_mode`: managed-isolated / managed-local / external-unverified; отдельно `provenance` и ручная аттестация. Способ запуска не является сам по себе ни оценкой правдивости, ни основанием для автоматической приёмки.

Eligibility переноса — вычисляемая функция политики и текущих inputs, а не пользовательский переключатель. Локальный hash детектирует изменение в заданной модели, но не доказывает авторства и правдивости отчёта. Старые `checked` мигрируют в `stale/unverified`, если новых зависимостей нет. Требования вначале утверждаются на исходный кандидат, затем формируется и проверяется именно единый delivery snapshot (§16).

Для CLI предусмотреть стабильный JSON envelope и коды ошибок. В течение переходного периода удерживать старые статусы и коды там, где не вводятся в заблуждение; versioned v2-дополнение и таблица преобразования — в документации. Не переименовывать `INCOMPLETE` в `PASS` без изменения смысла. При ошибке записи отчёта после выполненной операции возвращать отдельный код/структуру с фактом `operation_applied=true` и путём журнала; старый потребитель не должен интерпретировать это как «ничего не произошло».

### 4.3. Модель разрешений выполнения

- `external-reference`: вручную предоставленный URL, только диагностический, provenance непроверен без дополнительных подтверждений.
- `managed-local`: управляемая копия, запуск после проверки условий и риска в доверенной/подходящей среде, с честным предупреждением, что это не встроенная ОС-песочница.
- `managed-isolated`: используемый backend реально проверил доступные ограничения файлов, сети и ресурсов; подробно перечислить проверенное и непроверенное. Просто установленный Docker, отдельная папка, `unshare` или флаг пользователя не подтверждают этот уровень.

Агент проверяет происхождение, скрипты, плагины, зависимости и среду; CLI требует явно выбранный режим исполнения и регистрирует подтверждение оценки риска согласно §20. При необходимости агент уточняет разрешение пользователя. **Не блокировать автоматически всю работу только из-за отсутствия Docker**, если подходящая доверенная среда фактически имеется; не запускать подозрительный код, когда требования безопасности нельзя обеспечить. Нет безопасного запуска — сохранять статический результат и явный блокер, не ослаблять политику молча. Визуальные результаты локального режима могут быть полезны, но не маркируются изолированными. Права на конечное принятие — у пользователя/принятой политики, не у эвристики CLI.

### 5.3. Manifest как единый источник истины

- [ ] JSON — canonical. Markdown — regenerable представление, не источник решений; при нарушении согласованности CLI выдаёт диагностику и отдельную команду восстановления.
- [ ] Атомарная замена manifest на одной FS через временный файл, flush/fsync и replace, best-effort fsync директории, CAS по revision. Указать отличия Windows и ограничения отказоустойчивости.
- [ ] Lock с понятным владельцем/транзакцией и документированной recovery-командой; не удалять lock автоматически по одному таймеру или PID, не удостоверившись в возможности безопасного восстановления.
- [ ] Проверить partial writes и SIGKILL по контрольным точкам, два конкурирующих обновления, пересоздание Markdown, stale lock и отсутствие потери решений. `queue` не должен сам писать.

## 6. Этап 3 — анализ фактов и API решений

### 6.1. `analyze` и `discover`

- [ ] `analyze` принимает source root и возвращает inventory; множество package.json, отсутствие package.json и статический HTML — отдельные факты, а не автоматический запрет. При наличии нескольких проектов/entry points агент выбирает явно; инструменты не запускают произвольный пакет сами.
- [ ] AST/HTML discovery извлекает literals, imports, JSX attributes, link nodes, calls, conditions и диапазоны. Исключить автоматическое формирование записей страниц, output/title/id, распознавание hash-router по переменным, разворачивание массивов как доказанных страниц и назначение `/` главной страницей без решения агента.
- [ ] Не терять факты, слишком большие файлы, ошибки парсинга и динамические выражения. Ограничивать размеры и вывод с отдельным счётчиком и курсором; контекст доступен адресно. Адаптер документированной библиотеки допустим как источник типизированного наблюдения, не как решение о назначении. HTML-факты извлекать независимо от наличия tree-sitter: отсутствие JS/TS-парсера означает неполный охват этих языков, но не отмену доступного HTML-анализа.
- [ ] Отдельно формировать историю индексирования: новые/исчезнувшие факты; существующие решения не перезаписывать. При изменении исходника переоценивать актуальность подтверждений; не уничтожать старое обоснование.
- [ ] Тесты статического HTML, SPA, много package.json, вложенных файлов, сломанного AST, динамических роутов, JSX/TSX и R6. Проверить соответствие файлов discovery и source snapshot.

### 6.2. Полноценное редактирование manifest

Предлагаемые интерфейсы **являются проектом**, конкретные флаги будут закреплены при реализации и тестировании:

```text
queue list|show [фильтры]
queue page add|edit|remove
queue alias add|remove
queue state add|edit|remove
queue unresolved add|resolve|reopen
queue discovery confirm|reopen
queue apply --file <batch.json> --expected-revision <revision> [--dry-run]
queue render|recover
```

- [ ] Для каждой операции валидировать идентификаторы, пути, Unicode, коллизии маршрутов/output и зависимости; изменения применять целиком или не применять. Сохранять происхождение и обоснование смысловых решений; не генерировать их за агента.
- [ ] При удалении страницы/состояния: показать ссылки, влияние на coverage, предложить логическое удаление с причиной; необратимое удаление и потеря пользовательского содержимого требуют отдельного подтверждения. Для unresolved использовать ID, а не совпадающий маршрут как единственный ключ.
- [ ] Глобальное подтверждение допустимо только после разбора всех явно известных неоднозначностей; не означает автоматического доказательства полноты. Сохранять прочие неопределённости/ограничения как видимые вопросы.
- [ ] `queue`/`queue list` без записи; `queue render` — явное обновление производного Markdown; freshness вычисляется либо сохраняется через явное действие. Фильтры/pagination и подробный запрос по ID.
- [ ] Тесты повторного discovery, CAS, конфликтов batch, смены алиасов и output, восстановления и ручного решения; старые `queue-update` как совместимый адаптер до завершения миграции.

### 6.3. Инвалидация

Реализовать версионированную таблицу зависимостей и тесты:

| Что изменилось | Что устаревает минимум |
|---|---|
| source snapshot или способ получения эталона | подтверждение inventory требует пересмотра; browser/manual, зависящие от эталона, stale |
| output, route, alias страницы или её обязательные состояния | проверки соответствующей страницы и eligibility сайта; при неизвестной зависимости — всех страниц |
| scenario bytes, обязательность состояния, viewport/assertion policy | browser/ручное покрытие соответствующих требований; регистрация больше не подтверждает старый план |
| любой доставляемый HTML/CSS/JS/asset | статический, браузерный и ручной результаты для зависимых страниц; при неизвестных зависимостях — весь сайт |
| версия инструмента/среда/порог, влияющие на доказательство | соответствующий run stale или требует переоценки в соответствии с версионированной политикой |
| файл доказательства изменён/исчез | данное доказательство stale/unknown |

На первом этапе лучше консервативно инвалидировать больше результатов. Уменьшать охват инвалидации только после доказанного графа зависимостей и тестов. Допустимо продолжать работу с неполными проверками, но не называть их выполненными.

## 9. Этап 6 — безопасный локальный перенос `publish`

### 9.1. Контракт операции

1. `plan`: валидировать входы, наличие и происхождение проверок, покрытие, политику и candidate delivery snapshot; зафиксировать ревизию manifest и текущий snapshot существующего `vanilla/`. Показать полный состав и исключения, размер, diff, нужное разрешение и тип локальной копии. Plan не меняет `vanilla/`.
2. До записи убедиться, что цель разрешена, есть место/права, рабочая и целевая области позволяют выбранный механизм, а журнал и отчёт зарезервированы. `--replace-existing` не заменяет оценки риска: при возможной потере пользовательских данных агент получает явное разрешение пользователя.
3. `apply`: проверить, что plan и snapshot входов/цели не изменились; захватить lock и повторить проверки; копировать ранее подготовленный и проверенный delivery snapshot (§16), сверить каждый файл и запретить неожиданные файлы.
4. Создать и проверить **локальную** резервную копию цели, записать journal фаз; переносить только согласованный snapshot. Перед каждым разрушительным переходом сохранять достаточно информации для восстановления. Проверить результат после копирования и статическую согласованность с подтверждёнными страницами.
5. При исключении восстановить прежнюю цель по journal, насколько это допускает ОС; если восстановление невозможно — сохранить всё доступное и сообщить точное состояние и дальнейшие шаги. При прерывании процесса/машины специальная `recover` показывает состояния, не удаляет ничего без явно выбранного действия.
6. После переноса повторить необходимые проверки фактической `vanilla/`, сообщить результаты; локальная копия не является внешним резервом и не заменяет согласованную политику backup.

### 9.2. Fault injection и границы

- [ ] Тестировать отсутствие цели, запрет замены, сохранение старых файлов, изменения цели/кандидата после plan, блокировку каталогов Windows, cross-device, недостаток места и прав, отказ записи каждого journal stage и ошибки отчёта.
- [ ] SIGTERM/SIGKILL/рестарт между backup, rename и финальной проверкой; параллельные `publish` и изменения извне. Записать ожидаемое состояние и recovery для каждого шага; не обещать безусловную межплатформенную атомарность.
- [ ] Любой файл, фактически поставляемый в `vanilla/`, должен входить в snapshot и coverage соответствующего run. Никакая потеря исходной цели не маскируется сообщением о простом `BLOCKED`.
- [ ] При отсутствии нужного evidence — `publish` отказывает, но `staging` остаётся доступен как незавершённый результат; не принуждать пользователя принимать недостоверную проверку.

## 10. Этап 7 — модули, UX, документация и эффективность

### 10.1. Целевая разбивка кода

## 12. Тестовый план и обязательная матрица

### 12.1. Категории

1. **Unit и свойства:** валидаторы путей/routes/Unicode, schemas/canonical hashes, parsing и лимиты; state machine manifest и `publish`, lock/CAS, стабильные выходы команд.
2. **Fault injection:** запись отчёта, storage, crash/kill, диск/права, конкурентность, смена файлов, неполный journal, восстановление без потери пользовательских данных.
3. **Безопасность:** запрет dangerous types/path escapes, sandbox/profile capability tests, происхождение reference, запрет самосравнения как доверенного свидетельства, внешний доступ и потенциальные GET side effects. Ограничения честно документировать.
4. **Browser integration:** реальный Chromium, независимые локальные проекты, доступность/разные селекторы/сценарии, mismatch текста и изображений, длинные страницы, разные размеры, шрифты, липкие элементы, сеть, отсутствие и падение сервера, очистка процессов.
5. **Кроссплатформенность:** Linux и реальный Windows runner для Node, Python, процессов, путей, lock, rename и `preview.bat`; другие ОС — только если заявлены и проверены. Проверять clean install pinned dependencies и browser executable.
6. **Проверка агента:** два принципиально разных экспорта, например static HTML с несколькими файлами и React/Vite с hash/динамическими маршрутами. Агент исследует источник, фиксирует факты/решения, находит недостающие страницы, формирует сценарии, верстает полный сайт, проводит визуальный и ручной осмотр. Вторая фикстура не наследует URL/селекторы/контент первой.
7. **Качество:** сохранение текстов/ассетов/семантики, прямые вложенные URL, мобильное меню, клавиатура, обязательные состояния, отсутствие выдуманных страниц и backend, наличие дублированных header/footer и CMS заготовок. Оценка изображений агентом, а не только процента diff.

### 12.2. Команды запуска

До появления новых тестовых entry points применять текущие команды (Linux-пример; зависимости и Chromium должны реально быть доступны):

```bash

Новые отдельные команды для integration/security/benchmark задокументировать после реализации, не представлять предлагаемые команды как уже доступные. Не запускать установку пользовательского проекта, preview или сетевые запросы в непригодной среде; фиксировать причины пропусков.

| Сценарий | Обязательное поведение |

| отчёт вне разрешённой области | отказ до любой мутации, точная ошибка |

## 16. Уточнённый основной pipeline: один снимок поставки

**Проблема исходной редакции:** она предлагала проверять staging, а исключения из состава поставки выбирать в `publish plan`. Тогда фактически проверялись бы одни файлы, а поставлялись другие. Код `tools/lifecycle.py:154–165` сейчас копирует весь staging, хотя fingerprint игнорирует часть директорий. Ниже — обязательный порядок, исключающий эту неоднозначность.

1. Агент создаёт и редактирует рабочий кандидат `source/.work/staging/<id>/`. Заканчивает исследование и явно утверждает состав страниц, состояний, алиасов и спорных ссылок в манифесте. Агент выбирает состав поставки; CLI показывает полный inventory и исключения, но не угадывает, какие пользовательские файлы нужны.
2. **До доказательных проверок** команда подготовки формирует новый закрытый для редактирования логикой инструментов `source/.work/deliveries/<id>/site/`: копия только выбранных обычных файлов по явной delivery policy. CLI фиксирует её полный `delivery_snapshot_id`. «Закрытый» здесь — конвенция и проверка хешем, а не ОС-гарантия неизменности. Если агент меняет дизайн, формируется новый snapshot; старые проверки остаются историей.
3. `check`, browser-run и ручной осмотр относятся **именно к этому materialized delivery**, включая `template/` и все assets, а не к разным деревьям до и после отбора. Сервер кандидата обслуживает только его. Каждый run привязан к одному `delivery_snapshot_id`; при несовпадении файла или состава — stale/отказ.
4. `publish plan` ничего не исключает и не добавляет из проверенного delivery; показывает этот набор, его hash, требования, доказательства, target diff и backup. План содержит `plan_id`, `manifest_revision`, `requirements_hash`, `source_snapshot_id`, `delivery_snapshot_id`, `target_snapshot_id` или маркер отсутствия, сведения о требуемом разрешении и версии политики. Повторное изменение содержимого — новый plan и повтор проверки, а не незаметное обновление.
5. `publish apply` переносит в `vanilla/` **именно** проверенный полный delivery, включая все файлы, которые перечислены в snapshot. Финальное дерево побайтно и по составу сверяется с проверенным snapshot. Нет утверждения, что каждый бинарный файл прошёл визуальное исследование: snapshot доказывает состав и сохранность, coverage отдельно описывает реально выполненные проверки.
6. Отдельный post-publication run проверяет итоговый путь и раздачу; статус `published_unverified` возможен после успешного копирования до этой проверки, а не выдача полной приёмки. При неполном результате допустима передача staging/delivery как незавершённого результата без замены `vanilla/`.

Пути и названия приведены как **целевой контракт**, а не существующие директории/команды. Хранилище snapshots, сценарии и отчёты исключены Git по существующей политике; `source/.work/manifest.json` и `PAGE-QUEUE.md` разрешены, но на дату аудита являются untracked. Проверить итоговый `git status`/`git check-ignore`, не добавлять приватные данные в отслеживаемые файлы.

## 17. Конкретная спецификация snapshots и хешей

### 17.1. Исправление неоднозначности текущего fingerprint

`tools/core.py:46–55` добавляет `path + NUL + content + NUL`. NUL разрешён в бинарном содержимом: дерево с единственным файлом `a` и байтами `b'1\0b\x002'` даёт тот же поток байтов, что файлы `a = b'1'` и `b = b'2'`. Это **не криптографическая коллизия SHA-256**, а два различных входа с одинаковой сериализацией. В ходе аудита воспроизведено `fingerprint(first) == fingerprint(second)`.

### 17.2. Snapshot v2

Выбрать фиксированный формат и тесты, не полагаясь на `repr()` или неупорядоченный словарь:

- Принимать только обычные файлы/каталоги; symlink, junction/reparse point, hardlink с `nlink > 1` и special files — явный `BLOCKED` в базовом профиле. Платформенно недоступную проверку отображать как `unknown` и отказывать в promotion, если она нужна для безопасности.
- Для каждого файла: оригинальный относительный POSIX-путь UTF-8 без `.`/`..` и NUL, `size` в байтах, SHA-256 содержимого в hex и тип `file`. На файловой системе с непредставимым в Unicode именем — диагностировать и остановить snapshot, а не заменять символы; нормализацию NFC/casefold использовать для поиска коллизий, **не переименовывать исходный путь**. Коллизия при предполагаемой целевой платформе — диагностика и отказ до переноса.
- Записи сортируются по UTF-8 байтам исходного пути. Зафиксировать, входят ли пустые каталоги: в v2 delivery включить отдельные записи каталогов, чтобы точный состав не зависел от реализации копирования; source и delivery — разные `kind`/policy IDs. Сохранять для каждого файла только сведения, необходимые политике (не обещать перенос прав/ACL/mtime без отдельной спецификации).
- Корневой digest строится по доменно-разделённому, length-framed потоку: ASCII `htmlfromfigma.snapshot.v2\0`, затем `kind` и `policy_id` как `uint64_be(length) + UTF-8 bytes`, затем количество записей `uint64_be`, затем для каждой записи тип, путь, размер и hash: тип и путь — `uint64_be(length)+bytes`, размер — `uint64_be`, hash — **32 сырых байта** (для каталога размер 0 и hash из 32 нулевых байт). Вход за пределами допустимых длин/размеров — ошибка. Применить SHA-256 к всему потоку. Зафиксировать policy и список записей вместе с digest.
- Для requirements и сценариев отдельные domain tags. `requirements_hash` включает семантические обязательные страницы, маршруты/алиасы, output, состояния, применимость и assertions, утверждённые исключения/политику; **не включает** work status, время, run IDs и сам evidence, чтобы сохранение проверки не инвалидировало её циклически. JSON допускает только документированный набор структур/строк/целых/boolean/null, `NaN` и float исключить; UTF-8, `ensure_ascii=False`, `sort_keys=True`, `separators=(',', ':')`, без неявной Unicode-нормализации; порядок страниц/состояний и алиасов задаётся схемой явно и нормализуется только для семантически неупорядоченных множеств. Сценарии включают разрешённые действия, assertions и viewport. Ключи окружения/пороги — в отдельной версии policy/config hash, с тестами.
- Source inventory должен определять файлы **до** discovery; все действительно прочитанные файлы включая конфиги должны быть учтены. `.env`/секреты не читать и не копировать автоматически; если они нужны для запуска, показывать ограничение и получать явное решение, не сериализуя значения. Не обещать полноту при исключениях и ошибках чтения.
- До/после копирования и аудита пересчитывать снимок всех фактически используемых файлов; запуск и аудит привязать к идентификатору. Хеши не защищают от атакующего с теми же правами на все файлы/память и от всех TOCTOU; фиксировать threat model.

Обязательные тест-векторы: воспроизведение R10 (два дерева дают разные v2 digest), пустой файл/каталог, вложенные пути, русские и нормализационные формы, перемена длины и содержимого, порядок добавления файлов, добавление/удаление, разные kind/policy IDs, одинаковые результаты на Linux/Windows. Опубликовать в тестах конкретные expected hex, рассчитанные **независимым** проверочным encoder, не только сравнивать функцию с собой. Текущий v1 отпечаток хранить для истории; новый v2 при миграции создаёт новые evidence, а не объявляет v1 эквивалентным.

## 18. Контракт манифеста, состояния и миграции

### 18.1. Доменные инварианты v2

- `schema_version=2`, `revision` — монотонное целое, которое увеличивается на 1 при успешной транзакции manifest; явный `source_snapshot_id`, `requirements_hash`, `discovery` и коллекции `pages`, `unresolved_links`, `checks/runs`. Проверки не изменяют requirements hash, но меняют revision; CAS сравнивает полную ревизию, eligibility сравнивает семантический hash.
- Page: стабильный ID, title, source route + `reference_aliases`, один relative HTML output, `confirmation`, `work_status`, states, доказательные ссылки/обоснование и история. Начальное состояние `initial` — отдельная обязательная строка покрытия, но не требовать заносить его как сценарий с ID `initial` (v1 `load_scenarios` прямо запрещает такое имя). Каждый выбранный route/alias тестируется явно по policy; applicability не расширяется автоматически.
- Состояние содержит ID, `required: bool`, связанные scenario IDs/хеши, применимые конкретные пары viewport `(width,height)` и список assertions; для применимых по смыслу экранов требуется **явное** подтверждение агента, CLI не угадывает отсутствие кнопки по ширине. Убирается текущее ограничение одного сценарного файла на страницу, при этом старый v1 scenario format читается и переносится в явную v2 модель без исполнения.
- `unresolved_links` v1 и `discovery.unresolved` — не одно и то же: первое список объектов, второе свободные заметки, и нынешний `validate()` не проверяет заметки при confirm. В v2 для каждого объекта — стабильный ID, тип `decision_required|limitation|info`, контекст/источник, статус и обоснование. Только явно объявленные `decision_required` блокируют подтверждение; ограничения остаются видимыми и могут блокировать **конкретное покрытие**, а не уничтожают все операции. Агент классифицирует старые свободные строки; миграция не делает вывод за него и не удаляет их.
- `missing`, `duplicate`, `not-a-page`, другие согласованные решения — явные записи с причиной; для duplicate указать выбранную цель, если она известна. Внешняя/отсутствующая страница остаётся вопросом или явно решённой ссылкой, не становится обязательным HTML без решения.
- Ручное attestation имеет явное `actor=agent|user`, время, объект, действия/результаты, ограничения и ссылку на run; это самостоятельное утверждение, допустимое для требования ручного осмотра, но не автоматическое browser-pass.

### 18.2. Точные переходы

- `discovery unconfirmed → confirmed` только после ручного агентного исследования, отсутствия открытых `decision_required`, наличия >=1 страницы, подтверждённых каждой страницы и обоснования. CLI проверяет структуру и полноту заполнения, но не смысл.
- Изменение source → новый snapshot, inventory переоткрывается; страницы и прежние решения сохраняются с признаком необходимости пересмотра. Сценарии, подтверждения или факты не удаляются. Решение считать страницу по-прежнему существующей принимает агент.
- Изменение requirements → новый `requirements_hash`; все относящиеся к изменившимся требованиям проверки становятся stale. На первой реализации — консервативно все checks сайта; позже можно оптимизировать при доказанном dependency graph.
- Только completed run c полным необходимым coverage и outcome `pass`, current snapshot/config/requirements и приемлемым provenance может удовлетворять машинному требованию. `review`, `fail`, `partial`, `unknown`, `blocked` не приравниваются к pass. Доказательность относится к заданному тесту, а не к идеальности сайта.
- `queue list/show` не создаёт `.work`, не переписывает manifest/Markdown и не сохраняет stale-статусы. Считать текущую freshness можно в памяти; указывать `unknown`, если ресурс проверить невозможно. Отдельный явный `queue render` восстанавливает Markdown, `queue recover` — управляет журналом/lock.

### 18.3. Миграция и тесты к существующим данным

1. V1 reader должен принимать фактические поля, включая `source.fingerprint_version`, `discovery.hints`, `discovery.unresolved`, page `evidence`, `issues`, `checks` и необязательный `check_evidence`. Предварительная очередь на дату аудита: 15 страниц в статусе `confirmed`, глобальный discovery `unconfirmed`, 67 записей states, 4 `unresolved_links`; это текущие данные, не универсальные настройки.
2. `dry-run` читает v1, не меняет никаких project data; выдаёт изменения и список потенциально потерянных полей. Unknown fields сохраняются в `legacy_v1` или миграция останавливается; предпочесть сохранение, если валидация гарантирует round-trip. Все page-confirmations/работа/состояния и все заметки сохраняются; глобальный `unconfirmed` не меняется на confirmed. Checks `not_run` остаются `not_run`, ранее записанные результаты без полных v2 зависимостей становятся `stale/unverified` с сохранением истории.
3. Проверить migration на копиях реального файла и фикстурах с unknown fields; сохранить идентичность всех исходных значений после извлечения из v2 или предоставить документированное соответствие. Перед применением — backup JSON и Markdown, digest, ревизия и список файлов; `apply` должен отказаться, если v1 изменился после dry-run. Текущую очередь не считать согласованной и не заменять без безопасного завершения миграции.

## 19. CLI-контракт и план выпуска без ложной совместимости

**Предлагаемые интерфейсы в §§6, 16 и ниже — целевые, пока не реализованы.** Для реализации выбрать один внешний контракт и закрепить в `--help`/тестах в том же изменении; не оставлять реализацию между несовместимыми режимами.

|---|---|---|

| `discover --source` | собрать facts; **не** добавлять pages/не назначать outputs; создание пустого v2 manifest — отдельная явная операция | существующий v1 manifest не менять и не дополнять эвристиками; явное сообщение о миграции |

| `browser-audit-site --reference-url` | внешняя ссылка или managed reference, один процесс на пакет | внешний reference по умолчанию `external-unverified`; candidate binding отдельно |

| `publish --site` | сначала plan, затем отдельный apply по plan ID; recover для journal | до полной интеграции evidence/snapshot выпускать в fail-closed режиме, не запускать устаревший путь v1 |

### Статусы и коды выхода

Минимальный v2 envelope: `schema_version`, `command`, `operation` (`not_applied|applied|unknown`), `execution`, `coverage`, `outcome`, `freshness`, `issues`, `warnings`, `artifacts`, `next`. Для диагностических и read-only команд `operation=not_applied` означает отсутствие **доменных мутаций**, но создание запрошенных отчётов отражать в `artifacts` и документации. Определить точные nullable-поля схемой.

Базовые коды: 0 — успешно завершённая операция без проблем по её собственному контракту, **не** общая приёмка сайта; 1 — проверка выполнилась и выявила несоответствие; 2 — выполнено частично/требуется review; 3 — действие заблокировано до мутации или результат неизвестен до безопасного выполнения; 4 — внутренний/IO сбой, при этом JSON и журнал должны отдельно сообщать `operation=applied|unknown|not_applied`. Печатать JSON даже в post-operation failure в `--json` режиме, если stdout доступен; если и stdout, и журнал недоступны, никакой гарантии восстановления отчёта не обещать. Legacy команды по возможности сохраняют прежний `INCOMPLETE=2`, `FAIL=1`, `BLOCKED=3`; новый код 4 и отличия документируются и тестируются. Нельзя выдавать 0 как сигнал полной приёмки.

### Порядок безопасного включения

1. До готовности новых проверок, при выпуске обновлённого CLI отключить старые небезопасные ветки `publish`/`record-check checked` либо заставить их явно отказывать с миграционным сообщением; диагностические команды продолжают работать. Не оставлять переходное окно, в котором старые проверки обходят новые инварианты.
2. Добавить v2 readers/writers, только затем migrator с dry-run и backup, затем новую логику queue и executable runner; legacy JSON не переписывать автоматически при обычном просмотре.
3. Подключить run/evidence к v2, delivery и проверкам, затем включить `publish plan/apply` по строгому eligibility. Старый синтаксис `publish --site` должен либо безопасно создавать только plan с явной диагностикой, либо явным образом отказывать — не делать apply без нового контракта; выбрать и документировать один вариант. Рекомендуемый безопасный default — **только plan**.
4. Все изменения контрактов снабжать интеграционными тестами обеих веток; ранее предполагаемое «полное сохранение совместимости» не должно трактоваться как обещание сохранить небезопасный путь.

## 20. Конкретная модель проверок, окружения и разрешений

### 20.1. Eligibility для локального `publish`

Базовая политика v2: глобальная инвентаризация подтверждена, все обязательные страницы/маршруты/состояния явно выбраны, нет нерешённых блокирующих вопросов, проверенный delivery совпадает с планом; есть актуальные static/browser runs и ручная attestation с требуемым coverage; ни один обязательный результат не `fail/review/partial/unknown/stale`; нет нерешённых обязательных локальных ресурсов. Иные предупреждения остаются видимыми и агент оценивает их влияние. Missing optional/fallback ресурс может оставаться заметкой с обоснованием, если требование к готовой поставке явно допускает fallback; нельзя автоматом считать обязательный отсутствующий файл необязательным.

При внешнем эталоне CLI не утверждает происхождение по URL. Допустимая для такой политики ручная аттестация provenance должна содержать, **как** проверена связь с source snapshot, кто проверил, ссылку на источник/артефакты и ограничения. Это зафиксированное утверждение, а не криптографический факт. Если аттестации или доказательств нет — browser результат остаётся диагностическим и не удовлетворяет eligibility. Managed-local и managed-isolated должны сами регистрировать тип запуска и связь с копией/процессом, но не дают гарантии защиты от злонамеренной подмены одним и тем же пользователем.

В локальной модели общий пользователь может переписать run store, manifest и данные процесса. Поэтому требование «JSON невозможно подделать» технически не обеспечивается простым форматом, `run_id` или hash. Защита в базовом режиме — от случайного импорта/перепутывания и несогласованных данных; для независимой достоверности нужен отдельный доверенный исполнитель и защищённое хранилище/ключи. Тесты проверяют запрет **импорта произвольного отчёта как автоматически выполненной проверки через CLI**, но не обещают защиты от владеющего рабочей директорией противника.

### 20.2. Выбор запуска и сетевая топология

- Автозапуск не должен требовать от пользователя каждый раз указывать селекторы или вручную поднимать сервер; агент выбирает профиль на основании происхождения и проверенной среды. `managed-local` требует явного указания профиля и записанной оценки риска, без обязательного дополнительного вопроса пользователю при обычном полномочном использовании. Секреты в env/доступных путях и чувствительные сервисы — основание для отказа либо использования проверенного isolated backend. Нельзя считать любую облачную песочницу безопасной на основании названия.
- По умолчанию не выполнять неизвестные npm scripts. Для поддержанного Vite запускать проверенную явно выбранную точку входа; конфигурация/плагины **всё равно исполняются**, регистрировать этот риск. Node 22 и pnpm 10.34.3 указаны текущим `source/.mise.toml` — это свойства текущего экспорта, не универсальные требования. Доступ к npm registry для install и сети при выполнении — отдельные фазы и правила, не включать произвольный egress неявно.
- При net namespace свой loopback не виден host runner. Поэтому архитектуру утвердить по проверке среды: либо размещать управляемые reference, candidate и Playwright в одном ограниченном sandbox, либо использовать минимально открытый контролируемый канал/прокси к reference. Нельзя считать хостовый `127.0.0.1` и namespace-loopback взаимно доступными. Фиксировать, что реально ограничено; если канал не построен — конкретный blocker.
- Привязка процесса и порта: запускать Vite на свободном порту, опрашивать PID/выход/порт и проверять, что endpoint принадлежит запущенному процессу в пределах возможностей ОС; при конфликте отказаться/повторить, **не** открывать посторонний listener. Race-free резервирование порта не обещать без поддерживаемого механизма передачи заранее открытого сокета.
- Для Arena user-facing preview процесс должен жить до закрытия пользователем и слушать допустимый `0.0.0.0`, быть защищён от утечек `.work/`, иметь корректный Vite host/origin; не подменять им приватный browser audit. Для короткого batch audit управляемый процесс останавливать. Если CLI исполняется как one-shot процесс, нельзя одновременно обещать долгоживущий preview после его завершения: использовать платформенный process manager или документировать отдельный режим и lifecycle.

### 20.3. Browser coverage без чрезмерного декартова произведения

Матрица строится по **явно применимым** комбинациям, утверждённым агентом: не обязателен каждый alias × каждое интерактивное состояние на всех размерах, если это не требуется политикой. Каждая страница по умолчанию получает initial на трёх размерах; alias и прямой переход — явно запланированные навигационные проверки, каждый обязательный state — на отмеченных применимых viewport. Для каждой строки отчёт содержит `planned`, `executed`, outcome и причину skip. Отсутствие сценария для mandatory state — `partial`, а не полный pass; конкретные селекторы и assertions агент задаёт по источнику.
